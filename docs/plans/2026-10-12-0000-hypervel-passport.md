# Passport port design — `hypervel/passport`

This record describes the Laravel Passport port into `src/passport`, namespace `Hypervel\Passport`, for Hypervel 0.4. It explains the package's architecture, intentional upstream differences, framework integrations and regression coverage. Application guidance lives in `src/docs/passport.md`; upstream synchronization starts from `docs/upstream-sync/sync.yaml` and `src/passport/README.md`.

This is the initial Hypervel Passport package, so no earlier Hypervel Passport data format needs compatibility shims. Laravel applications migrating to Hypervel follow the porting guide. The package supplies generic extension points for application-specific authorization and OpenID Connect implementations; it does not implement OpenID Connect itself.

Exploratory PHP CLI measurements used to identify expensive operations during design (indicative values, not throughput guarantees):

| Operation | Cost |
|---|---|
| PBKDF2-SHA256, 100k iterations (league password mode, per encrypt/decrypt) | ~96 ms |
| bcrypt cost 12 `password_verify` (client secret check) | ~185 ms |
| RSA-4096 sign (access token issue) | ~3.7 ms (acceptable, unchanged) |
| RSA key parse (`openssl_pkey_get_private()` / `_public()`, 2048 or 4096-bit) | ~0.4–0.5 ms |
| AES-256 decrypt + HMAC of a 4096-bit private key PEM | ~0.02 ms |
| RSA verify with an already-parsed public key | 2048-bit ~21 µs; 4096-bit ~61 µs |
| RSA key generation (`openssl_pkey_new()`) | 2048-bit ~140 ms; 4096-bit ~1.25 s |

In Swoole these are CPU-bound and block every coroutine on the worker for their duration.

## Upstream baseline and framework behavior

- league `AuthorizationServer`, `ResourceServer`, `BearerTokenValidator` and all grants hold only configuration; `respondToAccessTokenRequest()` clones the response type per request (`getResponseType()`). Sharing them across requests is safe.
- Hypervel `once()` (`src/support/src/Once.php`) is coroutine-scoped (`CoroutineContext`), so upstream `ClientRepository::find()`'s `once()` is per request; it can't be cleared per client, hence E's own memo.
- Hypervel's URL generator reads the request from `RequestContext` (`UrlGenerator::getRequest()`), so `route()` called while building a worker singleton bakes in that request's host.
- Hypervel controllers and middleware are auto-singletons (worker lifetime).
- Hypervel auth guards are cached for the worker in `AuthManager::$guards`; explicit user state stays in `CoroutineContext`, while token/request guards cache resolved users in RequestContext's request-scoped values and resolve the request per call (no `setRequest()`).
- `AuthManager::getAuthContextKeys()` collects each guard's durable keys; `MakesHttpRequests` carries those across simulated test requests. Resolved per-request caches must not be listed.
- League's `BearerTokenValidator::validateAuthorization()` only reads the `authorization` header and returns the request with `oauth_*` attributes.
- League `AuthCodeGrant::respondToAccessTokenRequest()` calls `isAuthCodeRevoked()` (in `validateAuthorizationCode()`) before checking the code's client and redirect URI, and checks PKCE after that; then it calls the protected `issueAccessToken()`, `issueRefreshToken()` and finally `revokeAuthCode()`. `DeviceCodeGrant` likewise calls `isDeviceCodeRevoked()` before its client check. `RefreshTokenGrant` calls `isRefreshTokenRevoked()`, then `revokeAccessToken()` for the old access token on every refresh and (if rotation on) `revokeRefreshToken()` before issuing. `AuthorizationServer::respondToAccessTokenRequest()` builds and signs the response after the grant has persisted the tokens.
- League's `ResourceServer::getAuthorizationValidator()` calls `BearerTokenValidator::setPublicKey()` on every request, which rebuilds the lcobucci configuration and constraints. `BearerTokenValidator::initJwtConfiguration()` is private and hard-codes `new Sha256()`, and lcobucci's `OpenSSL::getPublicKey()` / `getPrivateKey()` are private, so the PEM is parsed on every verify and sign (~400 microseconds, see the measurements).
- League `DeviceCodeGrant::issueDeviceCode()` is `protected` and receives the verification URI as an argument; it is the only consumer of the constructor's `$verificationUri`.
- Hypervel query grammars compile `whereJsonContains` as: Postgres `(col)::jsonb @> ?`, MySQL/MariaDB `json_contains(col, ?)`, SQLite `exists (select 1 from json_each(col) where json_each.value is ?)` — all work on `jsonb` / `json` columns and on `text` columns holding JSON.
- `Hypervel\Cookie\Middleware\EncryptCookies::serialized()` and `CookieValuePrefix` exist (cookie paths port directly).
- `bin/run-database-tests.sh` discovers `tests/Integration/<Package>/Database/<Driver>` automatically; `bin/split.sh` splits every `src/*` directory automatically.
- Foundation `config/auth.php` ships `web`, `sanctum`, `jwt` and `passport` guards (no `api` guard).
- Laravel MCP uses: `ClientRepository::createAuthorizationCodeGrantClient(name:, redirectUris:, confidential:, enableDeviceFlow:)` (named args), `Passport::$scopes` / `Passport::tokensCan()`, route names `passport.authorizations.authorize` and `passport.token`, client attributes `id`, `grant_types`, `redirect_uris`, optional `scopes`. Keep all of these intact. MCP uses none of the removed APIs below.
- league requires `lcobucci/jwt` ^5.6 and signs and validates access tokens with it (`AccessTokenTrait`, `BearerTokenValidator`). Firebase 7 (root `firebase/php-jwt` ^7.0), which upstream uses for the cookie JWT, rejects HMAC keys shorter than their hash size (`JWT::validateHmacKeyLength()`, 256 bits for HS256).
- `CryptKey::__construct()` parses the key (`isValidKey()`), and lcobucci parses it again on every sign and verify. League JWTs set no `kid` or `iss`.
- `AccessTokenTrait::convertToJWT()` is private, but the trait's public `toString()` calls it through `$this`, so a method with the same name on Passport's `Bridge\AccessToken` replaces it.
- League calls the redemption checks (`isAuthCodeRevoked()`, `isRefreshTokenRevoked()`, `getDeviceCodeEntityByDeviceCode()`) before `issueAccessToken()` in the same request; `BearerTokenValidator` calls `isAccessTokenRevoked()` for every bearer validation.
- Session cookie attributes are resolved per request: `StartSession::resolveCookieConfig()` applies `StartSession::configureSessionCookieUsing()` callbacks. Sanctum registers one; applications can customize cookie attributes through the same mechanism.
- Key and certificate changes need a full restart of the server and other long-running processes; `server:reload` keeps inherited application state (`src/docs/deployment.md` "Reloading Services"; `hypervel/jwt`'s key commands print this warning).
- Worker-lifetime LRU precedent: `src/validation/src/RulePlanCache.php` (array insertion order as the queue; unset and reinsert on hit; evict `array_key_first()`).
- League `DeviceCodeGrant::respondToAccessTokenRequest()`: `getDeviceCodeEntityByDeviceCode()`, then `isDeviceCodeRevoked()`; a code with no user gets `persistDeviceCode()` (last poll) and `authorization_pending` / `slow_down`; an approved code gets tokens, then `revokeDeviceCode()`. User codes are 8 characters from `BCDFGHJKLMNPQRSTVWXZ`. League retries code, token and device-code generation when persistence throws `UniqueTokenIdentifierConstraintViolationException`; Hypervel's driver error is `Hypervel\Database\UniqueConstraintViolationException`.
- League's `BearerTokenResponse` calls the access token's `toString()` once per response; each call builds and signs a new JWT.
- Hypervel `RateLimiter::for()` replaces an existing named limiter; `ThrottleRequests` uses a named limiter when given one name, otherwise 60 per minute keyed by user or IP.

## Decisions

### A. Removed upstream surface (legacy and tech debt)

**A1. Implicit and password grants — removed.**
Why: RFC 9700 prohibits the password grant and recommends against the implicit grant; OAuth 2.1 draft 13 omits both. Replacements are authorization code with PKCE (League requires PKCE for public clients by default), device authorization for input-constrained devices, and Sanctum or JWT for first-party applications. Keeping the legacy grants as opt-in features would preserve their security risks without serving a compatibility requirement for this new package.
Remove: `Passport::$implicitGrantEnabled`, `$passwordGrantEnabled`, `enableImplicitGrant()`, `enablePasswordGrant()`; provider `makePasswordGrant()`, `makeImplicitGrant()` and their `enableGrantType()` blocks; `Bridge\UserRepository` and the model hooks it calls (`findForPassport`, `findAndValidateForPassport`, `validateForPassportPasswordGrant`); `ClientRepository::createPasswordGrantClient()`, `createImplicitGrantClient()`; `ClientCommand --password/--implicit` and their methods; `ClientFactory::asPasswordClient()`, `asImplicitClient()`; `'password'` from the `finalizeScopes()` grant list that may keep `*` (becomes `['personal_access', 'client_credentials']`); every `implicit` / `response_type === 'token'` / `useFragment` branch — `HandlesOAuthErrors::withErrorHandling(Closure $callback)` and `Exceptions\OAuthServerException::__construct(LeagueException $e)` lose the dead `$useFragment` parameter, and `loginRequired()` / `consentRequired()` / approve / deny controllers stop passing it.
Upstream tests `ImplicitGrantTest`, `PasswordGrantTest` and password/implicit cases elsewhere → `REMOVED:` comments.

**A2. Deprecated APIs — removed.** None appear in `passport.md` or MCP; the docs show only the replacements.

| Removed | Replacement |
|---|---|
| JSON API: `ClientController`, `ScopeController`, `PersonalAccessTokenController`, `AuthorizedAccessTokenController`, `Http/Rules/RedirectRule`, `Http/Rules/UriRule`, `TokenRepository`, `Passport::$registersJsonApiRoutes` and its routes block | App-defined routes using `$user->oauthApps()`, `$user->tokens()`, `ClientRepository::create*Client()` |
| `ClientRepository::findForUser()`, `forUser()`, `update()`, `delete()` (+ protected `clientsFor()`) | `$user->oauthApps()->find()`, `$user->oauthApps()`, model updates, `Client::revoke()` (F11) |
| `HasApiTokens::clients()` | `oauthApps()` |
| `Client::user()` | `owner()` |
| `Client::authCodes()` | — |
| `Token::user()` | — |
| `AuthCode::client()` | — |
| `Passport::setDefaultScope()` | `Passport::defaultScopes()` |

Upstream tests for these (`ClientControllerTest`, `AuthorizedAccessTokenControllerTest`, `PersonalAccessTokenControllerTest`, `ScopeControllerTest`, `RedirectRuleTest`, relevant cases elsewhere) → `REMOVED:`.

**A3. Pre-13 schema and upgrade helpers — removed.**
- `ClientRepository`: delete every `getColumnListing()` probe (a schema query on each create/update/list) and the `redirect` / `personal_access_client` / `password_client` / `user_id` branches; `create()` always writes `redirect_uris`, `grant_types`, and uses `oauthApps()` for owners.
- `Client`: drop `personal_access_client` / `password_client` casts, the `redirectUris()` and `grantTypes()` accessors (plain `array` casts remain), the `user_id` branch in `firstParty()` (becomes `empty($this->owner_id)`), and `initializeHasUniqueStringIds()`.
- `Passport::$clientUuids` — clients are always UUIDs (migration is `uuid('id')`, other tables use `foreignUuid('client_id')`). This also removes the integer-ID collision class (laravel/passport#1912). Keep the model-driven unique-ID validation in `ClientRepository::find()` (supports custom client models with another unique-ID trait).
- `passport:hash` command.
- `TokenGuard`'s legacy `expiry` cookie-claim check (the cookie also changes name, so legacy cookies never arrive).

### B. Coroutine and worker-lifetime fixes

**B1. `TokenGuard` rewritten for worker-lifetime caching** (pattern: `SanctumGuard`, `Hypervel\Auth\TokenGuard`).
- Constructor: `string $name` (from `extend('passport', fn ($app, $name, $config) => …)`), `ServerFactory` (I1), `PassportUserProvider`, `ClientRepository`, `Encrypter`, `Container $app`. No `Request`; resolve `$this->app->make('request')` per call, returning null when `RequestContext::has()` is false (as `SanctumGuard`).
- Remove `setRequest()` and the provider's `app()->refresh('request', $guard, 'setRequest')`. Laravel needs them because its guard holds one request; this guard is shared by every request on the worker and reads the coroutine's request from `RequestContext`. Rejected: keeping `setRequest()` as a coroutine-context override, which would let the guard authenticate a different request than `request()`, middleware and other guards see. `RequestContext::set()` replaces the coroutine's request and `validate(['request' => ...])` authenticates an explicit one.
- State in `CoroutineContext` (keys follow existing guards):
  - `__auth.guards.{name}.user.explicit` — `setUser()` / `actingAs()`; durable.
  - `__auth.guards.{name}.client.explicit` — `setClient()` / `actingAsClient()`; durable.
  - Resolved user and resolved client live in RequestContext's request-scoped values, keyed by a credential fingerprint: `xxh128` of the bearer token, or of cookie value + `X-CSRF-TOKEN` + `X-XSRF-TOKEN` for the cookie path. Use a static null sentinel object so "no user" is cached too. A new request clears resolved results even when its credentials are unchanged; fingerprinting also handles credential changes on the same request.
- Share bearer validation across guards and token middleware through `ServerFactory::validateAuthenticatedRequest(Request $request, bool $cache = true)`. One last-result record in coroutine context matches the request object, resource-server object and bearer fingerprint, retaining the validated PSR request or OAuth exception. This avoids duplicate signature and revocation checks for client-credentials requests and multiple provider guards, and misses after request, credentials, settings or test-fake changes.
- Implement the full Hypervel `Guard` contract (`hasUser()`, `setUser()`, `forgetUser()`), keep public `client()` / `setClient()` (the permission package calls `client()`), add `getAuthContextKeys()` returning the two explicit keys, keep `Macroable`, add `flushState()` (`static::flushMacros()`).
- `validate(array $credentials)`: authenticate `$credentials['request']` without reading or writing auth-result caches; pass `cache: false` to the factory. This preserves upstream's fresh check, including after revoking the token and validating the same request object again. Protected helpers take the `Request` explicitly so `user()` and `validate()` share them.
- Provider `makeGuard(string $name, array $config)` builds it; register through `callAfterResolving(AuthManager::class, …)` + `extend()` as `SanctumServiceProvider::configureGuard()` does.
- Client-credentials tokens: return no user when `oauth_user_id === oauth_client_id`, without upstream's extra `$client->hasGrantType('client_credentials')` condition. League sets `sub` to the client ID when a token has no user (`AccessTokenTrait::getSubjectIdentifier()`), and `EnsureClientIsResourceOwner` already uses the same marker. Upstream's extra condition only existed to tell integer client IDs apart from integer user IDs (laravel/passport#1912), which A3 removes. Without this change, a client-credentials token issued before the client lost that grant would send the client UUID to `retrieveById()`: Postgres throws, and MySQL converts the string to a number (its leading digits) for the comparison, so it can match an unrelated user.
- `client()` returns null on the cookie path. Upstream calls `findActive($token['aud'])`, but `ApiTokenCookieFactory` never writes `aud`, so a valid cookie raises an undefined-key warning (a 500 under the framework's error handler). A first-party cookie has no OAuth client. Test with a cookie made by the real factory (upstream's tests hand-build cookies with `aud`).
- Remove upstream's `catch (Exception)` around both `retrieveById()` calls. After C1's provider check, C2 and the client-token check above, the only IDs that reach the user provider come from the guard's own provider, so the catch only turns database and provider failures into 401s (fail fast).
- Remove upstream's `$this->request->headers->set('Authorization', '', true)` after a failed validation. Upstream uses it to stop repeated validation (and repeated reporting) on later `user()` calls in the same request. The null-sentinel cache does that here, and the mutation hides the token from other guards and middleware in the same request (e.g. `auth:passport,sanctum`; Hypervel Sanctum ignores a Passport JWT anyway because it lacks the `id|token` form).
- The guard also incorporates C1/C2's provider checks, omission of `report()` for invalid tokens (D4), header-only PSR requests (D3), per-request resource servers (I1), cookie binding (H4) and `token()` (H6).

**B2. `CreateFreshApiToken` — guard passed explicitly.**
Upstream sets `$this->guard` then calls `$next()`; the middleware is a worker singleton, so concurrent requests with different guard parameters read each other's value after the controller yields. Remove the `$guard` property; `handle(Request $request, Closure $next, ?string $guard = null)` passes it down: `shouldReceiveFreshToken(Request $request, Response $response, ?string $guard)`, `requestShouldReceiveFreshToken(Request $request, ?string $guard)`, and `$request->user($guard)` when making the cookie. Pass the guard to the cookie factory, which owns provider resolution (C2).

**B3. View responses are bound fresh per resolution.** `Passport::authorizationView()`, `deviceAuthorizationView()` and `deviceUserCodeView()` bind `SimpleViewResponse` as a singleton, and `withParameters()` stores the user, client, request and auth token on it, so one request's consent data stays on the worker and is visible to concurrent requests until rendered. Register them with `bind()`: the controllers resolve the response by method injection, so each request gets its own instance and `withParameters()` keeps upstream's behavior. The approved/denied device responses hold no request state and stay singletons.

**B4. Device verification URI resolved per request.**
Upstream passes `route('passport.device')` to `DeviceCodeGrant` when the `AuthorizationServer` singleton is built, so the first request's host is used for the worker lifetime. `Bridge\DeviceCodeGrant` resolves the URL per request, preserving each request's host and proxy prefix:

```php
class DeviceCodeGrant extends LeagueDeviceCodeGrant
{
    public function __construct(
        DeviceCodeRepositoryInterface $deviceCodeRepository,
        RefreshTokenRepositoryInterface $refreshTokenRepository,
        DateInterval $deviceCodeTTL,
        protected UrlGenerator $url,
        int $retryInterval = 5,
    ) {
        parent::__construct($deviceCodeRepository, $refreshTokenRepository, $deviceCodeTTL, '', $retryInterval);
    }

    protected function issueDeviceCode(DateInterval $deviceCodeTTL, ClientEntityInterface $client, string $verificationUri, array $scopes = []): DeviceCodeEntityInterface
    {
        // The grant lives for the worker lifetime, so build the URI from the current request.
        return parent::issueDeviceCode($deviceCodeTTL, $client, $this->url->route('passport.device'), $scopes);
    }
}
```

`makeDeviceCodeGrant()` builds it (keep `setRefreshTokenTTL`, `setIncludeVerificationUriComplete(true)`, `setIntervalVisibility(true)`, the `Route::has('passport.device')` guard). Test with two requests on different hosts against one server instance.

**B5. Other lifetime notes:** League servers and their `CryptKey`s are built once per settings set by `ServerFactory` (I1), not per request as in Laravel. Drop the redundant `singleton(ClientRepository::class)` (auto-singleton).

**B6. Authorization controllers resolve their guard per request.** Upstream's contextual binding injects `Auth::guard(config('passport.guard', null))` into `AuthorizationController` and `DeviceAuthorizationController`. They are worker singletons, so with a null `passport.guard` the first request's default guard would be kept for the worker lifetime. Applications can select their default guard through `Auth::shouldUse()` during a request; null must continue to mean that current default. The controllers inject `AuthManager` and the config `Repository` and call `$this->auth->guard($this->config->get('passport.guard'))` per request. The concrete manager is required for C1, C4, C8 and C9 to get the approving guard's provider from `getUserProviderName($this->config->get('passport.guard'))` through `ResolvesApprovingGuard` (C4). The routes' `auth` middleware also resolves per request.

### C. Upstream security fixes

**C1. Tokens record the user provider they were issued for.**
Upstream decides which provider a token's `sub` belongs to from its client, and accepts a client with `provider = null` on every Passport guard (`$client->provider && $client->provider !== …`). Auth-code, device and client-credentials clients are created with a null provider (MCP dynamic registration too), so with `passport` (users) and `passport-customers` guards, a token for user #5 authenticates as customer #5. Store the provider on the token instead:
- `provider` (nullable string) on `oauth_auth_codes`, `oauth_access_tokens`, `oauth_refresh_tokens` and `oauth_device_codes` (F9).
- Set from the approving guard's provider (B6) for auth codes and device approvals, through J1's authorization attributes; from `HasApiTokens::getProviderName()` for personal access tokens (`PersonalAccessTokenFactory` passes it the same way); null for client-credentials tokens. Tokens issued from a code, device code or refresh token inherit it (H3).
- `TokenGuard`'s bearer path compares the token's `provider`, read from the model H1 memoized (no extra query), with `$this->provider->getProviderName()` and returns no user when it differs or is null.
- `HasApiTokens::tokens()` filters `where('provider', $this->getProviderName())` instead of upstream's `whereHas('client', ...)` subquery; `hasGrantedScopes()` adds the approving guard's provider.
- `Passport::defaultProvider(): ?string` (`AuthManager::getUserProviderName(Passport::DEFAULT_GUARD)`, see F1) remains only for personal access clients stored with a null provider (F5, `ClientCommand`). `client()` keeps returning the client without a provider check (machine clients).
- Cost: none extra. The code and refresh-token reads that C3 already does carry `provider` (H3), and API requests read it from H1's memoized model.

**C2. Cookie JWT bound to a provider.**
The `CreateFreshApiToken` cookie carries only `sub`, so any Passport guard loads that ID from its own provider (same confusion as C1, by a logged-in user). Fix:
- `ApiTokenCookieFactory::make(string|int $userId, string $csrfToken, ?string $guard = null)` resolves the guard's provider once and adds a `provider` claim; null selects the current default guard. Two-argument calls keep working (`TransientTokenController` uses the default guard). A guard without a configured provider produces a null claim, never a fallback to another provider.
- `CreateFreshApiToken` passes its guard (B2).
- The factory takes `Config`, `ServerFactory`, `AuthManager` and `Container` instead of `Config` and `Encrypter`, and reads the current request per call. Protected `createToken()` receives a required nullable provider argument after `$expiration`; it never resolves or substitutes the provider itself.
- `TokenGuard` cookie path rejects tokens whose `provider` claim is missing or differs from `$this->provider->getProviderName()`.

**C3. Single-use auth codes, device codes and refresh tokens, issued atomically.**
Upstream checks `revoked` and revokes later, so two concurrent requests can both redeem one auth code, device code or rotated refresh token (RFC 6749 §4.1.2). And a failure between persisting tokens and sending the response leaves the grant used with no usable response.
- Revocation checks stay read-only. `isAuthCodeRevoked()`, `isRefreshTokenRevoked()` and `getDeviceCodeEntityByDeviceCode()` read the row once and record it in the issuance context (H3); `isDeviceCodeRevoked()` reads that record without a query. A wrong client, redirect URI or PKCE verifier therefore can't burn someone else's code.
- The claim runs after League's validation, right before issuance. `Bridge\AuthCodeGrant` and `Bridge\DeviceCodeGrant` override the protected `issueAccessToken()` to claim the recorded code with a conditional update (`whereKey(...)->where('revoked', false)->update(['revoked' => true])`), then call the parent. Refresh tokens are claimed the same way in `revokeRefreshToken()`, which League calls after validation. A claim that updates nothing throws `invalid_grant`, so one concurrent redemption wins. `revokeAuthCode()` and `revokeDeviceCode()` skip their query when the operation already claimed the code, so the query count matches upstream.
- Atomic issuance. `Bridge\TokenIssuance` opens a transaction on the credential connection at the issuance's first write after validation: the code claim; the refresh grant's `revokeAccessToken()` of the old access token, after taking C6's family lock; or, for personal access and client-credentials tokens, the first insert. `Bridge\AuthorizationServer::respondToAccessTokenRequest()` commits after the response is built and signed, or rolls back on any exception. The claim or revocation, the new tokens, their created events and the response (including a custom response type, J) succeed or fail together, and a failure leaves the code, the old access token and the refresh token as they were. A concurrent redemption waits on the claimed row, then fails. The device poll update and C6's reuse revocation never join this transaction, so they stay committed when the request fails.
- Ambient transactions: the poll timestamp and replay revocation must commit even when the request fails, which a caller's open transaction would undo. Redemption therefore refuses to run inside an open transaction on the credential connection: C3's read-only checks throw a `LogicException` before any write. The check uses the connection's new `hasApplicableTransaction()` (Framework integration), which, like after-commit callbacks, ignores the test-wrapping transaction, so `RefreshDatabase` tests keep working, and only looks at that connection. Personal access and client-credentials tokens join a caller's transaction normally. The models written atomically (tokens, refresh tokens, auth codes, device codes, refresh-token families, and signing keys with the database store) must share one connection; boot validation (console `booted`, server `AfterWorkerStart`, like E) compares their effective connections, treating null as the default connection. The client model may use another connection. Documented together, in Public differences and the porting guide.
- `AccessTokenCreated` and `RefreshTokenCreated` dispatch through `afterCommitOrNow()`.
- Device approvals: `persistDeviceCode()`'s approval update matched on ID only, so a code could be approved or denied twice, even after it expired. The update adds `whereNull('user_id')->where('revoked', false)->where('expires_at', '>', Date::now())` and throws `OAuthServerException::invalidRequest('user_code')` when it updates nothing.
- Rejected: a transaction around the whole token request. It would also roll back the poll timestamp and the reuse revocation, which would then need special cases.

**C4. A client with a provider only accepts that provider's users.** A client whose `provider` is set (e.g. an admin-only client) must not be authorized through a guard of another provider. `AuthorizationController::authorize()` compares it with the approving guard's provider (B6) before approving or rendering consent and throws `OAuthServerException::invalidClient($psrRequest)` on mismatch, rendered through `HandlesOAuthErrors` (the existing wrapper only covers `validateAuthorizationRequest()`, so the new checks and J4 get their own); `DeviceAuthorizationController::__invoke()` shows the same error as an unknown user code. Third parties choose the `client_id`, so this is a request error, not a configuration exception. A null client provider accepts any provider, since C1 records the provider on the token. `Http/Controllers/ResolvesApprovingGuard`, a small trait next to `RetrievesAuthRequestFromSession`, owns the approving guard (B6), its provider (C1) and this check; C8 and C9 use it too.

**C5. PKCE requires `S256`.** League accepts `plain`, and when a client sends `code_challenge` without `code_challenge_method` it assumes `plain` (`AuthCodeGrant::validateAuthorizationRequest()`). `plain` puts the verifier itself in the authorization request; RFC 9700 says clients should use a method that doesn't expose it, which today means `S256`, and MCP requires `S256`. League's verifier list is private, so add `Bridge\AuthCodeGrant extends AuthCodeGrant` (built by `ServerFactory`) overriding `validateAuthorizationRequest()`: when `code_challenge` is present and `code_challenge_method` isn't `S256`, throw `OAuthServerException::invalidRequest('code_challenge_method', 'Code challenge method must be `S256`.')` before calling the parent (the same error league raises for an unknown method). Codes then only ever carry `S256`.

**C6. Refresh-token reuse revokes the grant (RFC 9700 §4.14.2).** RFC 9700 requires refresh tokens for public clients (MCP clients are public) to be sender-constrained or rotated with reuse detection: when a used refresh token comes back, the server can't tell the attacker from the client, so it revokes the active one. League only rejects the reused token.
- Table `oauth_refresh_token_families` (`uuid('id')->primary()`, `timestamp('revoked_at')->nullable()`, timestamps) and an indexed `oauth_refresh_tokens.family_id`. Model `RefreshTokenFamily`, swappable through `Passport::useRefreshTokenFamilyModel()` / `refreshTokenFamilyModel()` / `refreshTokenFamily()` like the other models.
- A code or device exchange creates the family in `persistNewRefreshToken()` (with H3's attributes); refreshes inherit `family_id` (H3). On a refresh exchange, J6 returning false rejects the refresh with `invalid_grant` (C3's transaction rolls back), so a refresh never issues an access token without a linked refresh token.
- Reuse: `isRefreshTokenRevoked()` already reads the row (H3); when it exists and is revoked, revoke the family and return true. When C3's refresh claim loses a race, `Bridge\TokenIssuance` rolls back at once, then revokes the family and throws, so the revocation stays committed.
- Revoking a family is one transaction: lock the family and return if it is already revoked, preserving the first `revoked_at`. Otherwise mark it revoked, then revoke live refresh tokens and their access tokens in primary-key batches (with rotation off a family can have several live branches), with E's cache invalidation and F2's event. Scan all family members for linked access tokens, but skip already-revoked refresh writes and empty access-token batches.
- Race with a concurrent rotation: every refresh, rotating or not, locks the family row (`lockForUpdate()`, one primary-key read) when C3's transaction starts, before any token row is written, and fails when `revoked_at` is set. Revocation also locks the family row before the token rows, so the two take locks in the same order and can't deadlock; revocation waits for an in-flight rotation to commit and then revokes the new pair as well. SQLite serializes writers anyway.
- `passport:purge` keeps revoked refresh tokens until they expire (they are the reuse evidence) and deletes families with no refresh tokens left (F6).
- Turning rotation off (`Passport::$revokeRefreshTokenAfterUse = false`) only applies to confidential clients. With it off, public clients get no refresh tokens (`getNewRefreshToken()` returns null) and their existing refresh tokens are rejected (`isRefreshTokenRevoked()` returns true without touching the family), because RFC 9700 section 4.14.2 requires rotation or sender-constrained tokens for public clients.
- Docs: clients must not refresh concurrently with the same token (the second request revokes the grant).

**C7. Revoked or missing clients are rejected on every bearer path.** The guard checks `findActive()`, but `ValidateToken` (`CheckToken`, `CheckTokenForAnyScope`, `EnsureClientIsResourceOwner`) relies on league, which only checks the token row, so a revoked client's tokens keep working there. H1's lookup in `isAccessTokenRevoked()` also calls `ClientRepository::findActive($token->client_id)` (so H2 applies) and treats a missing client as revoked; the guard's own `findActive()` is then a per-request memo hit (E).

**C8. Only the user who saw a consent screen can approve or deny it.** The consent screen stores the League request (with the user) or the device code (with the user ID) in the session, and the approve and deny controllers complete it for whoever submits the matching `auth_token`. Login keeps session data (`SessionGuard` only regenerates the ID), so if A leaves a consent screen and B logs in on the same browser, B's approval issues a code for A to the client. `RetrievesAuthRequestFromSession` and `RetrievesDeviceCodeFromSession` compare the stored user identifier and J1's stored `provider` with the approving guard's current user and provider (`ResolvesApprovingGuard`), and treat a mismatch like a wrong `auth_token`: forget the session keys and throw `InvalidAuthTokenException::different()`. The four approve and deny controllers take `AuthManager` and the config `Repository` like B6.

**C9. Approval rechecks the client.** The stored League request carries a serialized client, redirect URI and scopes, and League's `completeAuthorizationRequest()` trusts that snapshot; `completeDeviceAuthorizationRequest()` reloads the device code but not its client. A client revoked, or a redirect URI removed, while the consent screen is open would still receive a code. Before completing either flow, the retrieval traits recheck the client through `ClientRepository::findActive()` (so H2 applies), C4's provider rule, that the client still allows the grant, and that the stored scopes still exist (both flows). For authorization codes it rechecks the effective destination with League's `RedirectUriValidator` against the client's current redirect URIs: the stored `redirect_uri`, or, when the request omitted it (League allows that for a client with one registered URI), the saved client's original default rather than its new one. Native-app loopback redirects keep League's variable-port matching. A failure throws an OAuth error without a redirect, so nothing is sent to a URI that's no longer allowed.

**C10. Middleware distinguishes Passport users and machine clients.** `ValidateToken` reads the current user once and only reuses its token when the user implements `OAuthenticatable`; plain session users and Sanctum users instead take the bearer-validation path, avoiding undefined methods and incompatible token types. `EnsureClientIsResourceOwner` requires an `AccessToken` whose user identifier equals its client identifier. Browser-cookie `TransientToken`s represent users, so they cannot authorize machine-client routes, even though the ordinary scope middleware continues accepting them. `actingAsClient()` uses the client's string identifier as the mock subject, matching real League tokens and B1.

### D. CPU and hot-path performance (no security reduction)

**D1. League encryption uses a `Defuse\Crypto\Key`, not a password string.**
Upstream passes the app key as a string, so league uses `Crypto::encryptWithPassword()` / `decryptWithPassword()`: PBKDF2-SHA256 with 100k iterations on every auth-code issue and exchange, every refresh token issue and redeem (~96 ms each, blocking the worker). Junk `refresh_token` or `code` values sent with a public client ID trigger it without credentials. Laravel kept password mode only because switching invalidates outstanding refresh tokens and auth codes.
Security: PBKDF2 only strengthens low-entropy passwords; the app key is random (16 or 32 bytes). Both modes use the same AES-256-CTR + HMAC-SHA256 construction.
`ServerFactory` (I1) builds the key once, app-wide, and passes it to every authorization server it builds:

```php
use Defuse\Crypto\Encoding;
use Defuse\Crypto\Key;

$key = Key::loadFromAsciiSafeString(Encoding::saveBytesToChecksummedAsciiSafeString(
    Key::KEY_CURRENT_VERSION,
    hash_hkdf('sha256', Passport::tokenEncryptionKey($encrypter), Key::KEY_BYTE_SIZE, 'hypervel-passport'),
));
```

`Passport::tokenEncryptionKey()` / `encryptTokensUsing()` keep their string signatures (F8 derives the cookie key from the same string). Document that an `encryptTokensUsing()` callback must return random key material, not a password, and the same value for the worker lifetime: `ServerFactory` derives both this `Key` and the cookie key (F8) from it once per worker and owns both. Porting note: refresh tokens and auth codes issued by Laravel Passport cannot be decrypted (users authorize again; access tokens stay valid if the RSA keys are carried over and the imported token rows get `provider`, C1). Rejected: a separate `PASSPORT_ENCRYPTION_KEY` and key command, which add a secret to provision with no security gain over a key derived from the random app key.

**D2. Client secrets hashed with sha256, not bcrypt.**
Bcrypt verification (~185 ms) runs on every confidential-client token request (client credentials, refresh, code exchange) and can be triggered with any known client ID. Generated secrets are `Str::random(40)` alphanumeric ≈ 238 bits, so slow hashing adds nothing; Sanctum stores its 40-character tokens as sha256 (`src/sanctum/src/HasApiTokens.php`, `PersonalAccessToken::findToken()` with `hash_equals`). Weak secrets set by hand are not a supported path.
- `Client::secret()` mutator stores `hash('sha256', $value)` (null stays null) and still sets `plainSecret`.
- One method on `Client` owns verification (`secretMatches(#[SensitiveParameter] string $secret): bool` using `hash_equals()`), used by `Bridge\ClientRepository::validateClient()`; the bridge drops its `Hasher` dependency.
- No fallback for Laravel bcrypt hashes. Porting note: regenerate confidential client secrets (`ClientRepository::regenerateSecret()`) and reissue them.

**D3. Header-only PSR-7 request for bearer validation.**
`TokenGuard` and `ValidateToken` convert the whole request with `new PsrHttpFactory` on every API request (body stream copy, second JSON decode, uploaded-file streams, header/attribute clones) only so league can read `Authorization`. Add one small injected class (e.g. `Bridge\BearerRequestFactory`) used by both:

```php
public function make(Request $request): ServerRequestInterface
{
    $psrRequest = $this->factory->createServerRequest($request->getMethod(), $this->emptyUri);
    $authorization = $request->headers->get('Authorization');

    return $authorization === null ? $psrRequest : $psrRequest->withHeader('Authorization', $authorization);
}
```

`$this->factory` is a `Nyholm\Psr7\Factory\Psr17Factory`. Create one immutable empty URI in the constructor: bearer validation does not use the URL, so normalization and parsing add needless work. `ServerFactory::validateAuthenticatedRequest()` uses this conversion on a cache miss and validates through the server already selected, without resolving settings again; guards and middleware share that method (B1). Direct PSR resource-server callers retain their supplied request and resolve current settings. Controllers that type-hint `ServerRequestInterface` (token endpoints) keep using the routing binding.

**D4. No `report()` for invalid bearer tokens.**
Upstream reports league's `OAuthServerException` for every invalid, expired or revoked token (it is not in `internalDontReport`), producing an error log with stack trace per 401. Tokens are still rejected; this matches the framework not reporting `AuthenticationException`.

**D5. RSA keys are parsed once per worker.**
lcobucci parses the PEM on every verify and sign, and League's `ResourceServer` rebuilds its validator configuration on every request (verified facts). Measured: parsing a public key takes ~400 microseconds, against ~21 (2048-bit) or ~61 (4096-bit) for the verify itself, so parsing is most of the CPU of every bearer request.
- `Bridge\ParsedKey` implements lcobucci's `Key` (`contents()`, `passphrase()`) and also holds the parsed `OpenSSLAsymmetricKey`, checked once when it's built (RSA, at least 2048 bits, lcobucci's errors and OpenSSL failures). `Bridge\RsaSigner` is a stateless RS256 `Signer` that signs and verifies with the `Key` it's given: the parsed key when it's a `ParsedKey`, otherwise it parses `contents()` like lcobucci, so the `Signer` contract holds.
- `Bridge\BearerTokenValidator` implements League's `AuthorizationValidatorInterface` with League's validation logic (same parsing, `SignedWith`, `LooseValidAt`, claims and `isAccessTokenRevoked()` call) over the entry's map of parsed verification keys, choosing the key by `kid` (I2). `ServerFactory` builds one per settings entry and passes it to League's `ResourceServer` constructor, which then skips `setPublicKey()` because it isn't League's class.
- `Bridge\AccessToken::convertToJWT()` (I2) signs with the `ParsedKey` from `SigningCryptKey`.
- Parsed keys are read-only and openssl calls don't yield, so sharing them between coroutines is safe. Tests keep League's validator behavior (valid, expired, not-yet-valid, wrong-signature, wrong-algorithm, malformed and revoked tokens) and cover cross-verification with stock lcobucci in both directions, a different supplied key being rejected, malformed, wrong-type and short keys, encrypted private keys, and verification-only use.
- Sibling (Framework integration): `hypervel/jwt`'s `Providers\Lcobucci` caches a configuration with `InMemory` keys and stock OpenSSL signers, so its RS and ES algorithms parse the PEM on every request too. It gets the same treatment with its own package-local key and signers (ECDSA reusing lcobucci's signature converter), and `isAsymmetric()` stops relying on subclasses of lcobucci's `Rsa` / `Ecdsa`. No shared primitive: the common part is one OpenSSL call and a size check, and a shared lcobucci adapter would need a package both could depend on.

### E. Optional shared cache for access tokens and clients (Sanctum-style)

The cache removes repeated credential lookups. The overtrue cache-token package illustrated the demand but invalidated only through its repository's revoke path and hooked the deprecated `TokenRepository`, which Passport 13's guard no longer calls. Passport 13 still runs two primary-key queries per authenticated request (token revocation and client lookup), plus the user lookup. Warm Passport token/client caches eliminate the credential queries; eliminating the user query also requires the separate `EloquentUserProvider` cache. JWT signature and expiry checks still run.

Config (`config/passport.php`, Laravel-style section block):

```php
'cache' => [
    'enabled' => (bool) env('PASSPORT_CACHE_ENABLED', false),
    'store' => env('PASSPORT_CACHE_STORE'),
    'ttl' => (int) env('PASSPORT_CACHE_TTL', 300),
    'prefix' => env('PASSPORT_CACHE_PREFIX', 'passport'),
],
```

Design:
- One internal class owns enabled flag, store, TTL, key building, fill and invalidate, using `Hypervel\Cache\ModelCacheCoordinator` (fill lock; invalidation waits for the lock, so no stale refill) and reading through the write connection (`useWritePdo()`). `ModelCacheCoordinator::fill()` receives a lazy source-model closure. Its shared transaction predicate first checks the current transaction manager; only when an applicable transaction exists does it construct the model and call its non-borrowing `hasApplicableTransaction()` to check that source connection. Ordinary hits therefore construct no model, while transactions on another connection keep using the cache. An applicable source transaction bypasses cache reads and fills, preventing uncommitted publication, hiding the transaction's own writes, and republishing a stale transaction snapshot after another request's invalidation. Query builders stay inside cache-miss closures. Passport's per-request client/token memos use the same predicate, and supported writes clear affected entries immediately; the issuance context's saved model is separate. Test-wrapping transactions do not count, matching C3's ambient-transaction rule. Reference implementation: `src/sanctum/src/PersonalAccessToken.php` (`findTokenUsingCache()`, `invalidateTokenAfterMutation()`, `getCache()`, `getCacheKey()`).
- Access tokens: `isAccessTokenRevoked($tokenId)` → cached token model keyed by token ID (`cacheNull: false`), memoized per request (H1), so H1's callback and `$user->token()` read it without queries. Caching the model rather than a revoked flag matches Sanctum and lets H1 check owner columns on cache hits. Keys only come from signature-verified JWTs. JWT signature and expiry are still checked on every request.
- Clients: `ClientRepository::find()` supplies a class string and a miss-only lookup that constructs the model and validates its unique ID before querying. Request and shared-cache hits construct no model; no model prototype is retained between requests. Malformed IDs can incur cache reads and locking, as nonexistent valid IDs already do, but run no SQL and publish nothing (`cacheNull: false`). Cached models have relations unset. Passport-owned token/client memos in RequestContext's request-scoped values sit in front, and model events and package writes forget affected entries. A replacement request never inherits an earlier request's credential snapshots. H2's callback runs on the loaded model, so entries stay keyed by global client ID.
- Credential lookups use the writer with caching enabled or disabled: replica lag must not hide newly issued credentials or delay revocation. Test with different reader and writer data.
- Shared invalidation runs via `$connection->afterCommitOrNow()`; request memos clear immediately:
  - `Token` model `updated` / `deleted`. Creation clears only its request memo: missing rows are never shared, and new credentials have fresh identifiers.
  - Query-update paths: `Bridge\AccessTokenRepository::revokeAccessToken()`, `AccessToken::revoke()`'s fallback branch, and C6's family and race revocations.
  - `Client` model `updated` / `deleted` (covers revoke and `regenerateSecret()`). Creation only clears its missing-client request memo.
  - Relation writes: `HasApiTokens::tokens()` and `Client::tokens()` return `TokenRelation` (a `HasMany`) and `oauthApps()` returns `ClientRelation` (a `MorphMany`), following Sanctum's `PersonalAccessTokenRelation`, so `$user->tokens()->update(['revoked' => true])` and `$user->oauthApps()->delete()` don't leave live entries. Their `update()` and `delete()` hand the query to the cache class, which walks it in primary-key batches (`chunkById()`), writes each batch with `whereKey($batch)` and invalidates exactly those keys after commit. One transaction covers the walk, preserving atomic writes if a later batch fails. Batch selection stays bounded; after-commit invalidations retain the selected keys until commit. With the cache off they write directly and clear request memos. No events for these bulk writes, as with any Eloquent bulk write.
  - `passport:purge` needs none: purged tokens are revoked (stay revoked) or expired (JWT expiry rejects them).
- Serializable classes: `Cache::allowSerializableClassesUsing()` adds `Passport::clientModel()` and `Passport::tokenModel()` when enabled (see `SanctumServiceProvider::boot()`).
- Store validation like Sanctum: TTL > 0 and `ModelCacheStoreValidator::validate()` — on `booted` in console, on `AfterWorkerStart` in the server. Per-worker stores (array, worker-array) are rejected. The store must also be shared by every process that revokes tokens or changes clients: Redis or the database store across servers, the Swoole store only when all those writers run inside one server, and the file store only on a shared disk. The validator can't tell, so the docs say so.
- Documented limits: revocations through other bulk writes (`DB::table(...)->update()`, `Passport::token()->newQuery()->update()`) take effect when the entry expires; anyone with write access to the cache store could mark a token live (same trust boundary as sessions and Sanctum's cache). Off by default.
- Relations crossing the user/client/credential boundary use the configured related Passport model's connection, matching authentication and issuance, rather than inheriting the parent's connection. This covers `HasApiTokens::tokens()`, `oauthApps()`, `Client::tokens()` and `Token::client()`. Package queries avoid relation subqueries across these connections. Credential-to-credential relations keep normal Eloquent behavior because C3 requires a shared connection.

### F. Other agreed changes

**F1. Default guard named `passport`.** `api` is confusing next to `sanctum`. Replace every `config('auth.guards.api.provider')` (via `Passport::defaultProvider()`), default `Passport::actingAs()` / `actingAsClient()` `$guard` to `'passport'` (owning constant, e.g. `Passport::DEFAULT_GUARD`), add `'passport' => ['driver' => 'passport', 'provider' => 'users']` to `src/foundation/config/auth.php` and update its comment ("Install hypervel/passport to use the passport guard"). Docs use `auth:passport`. Update the permission package docs example (`$guard_name = 'api'`) and test config (`auth.guards.api`).

**F2. `AccessTokenRevoked` fires on every model and package revoke path.** Upstream fires it only from `Bridge\AccessTokenRepository::revokeAccessToken()` (refresh grant), not from the documented `Token::revoke()` or `$user->token()->revoke()`. Dispatch from the `Token` model `updated` hook when `revoked` changes to true, and explicitly from the query-update paths listed in E. Guard with `hasListeners()`. Dispatch through the same `afterCommitOrNow()` call as E's invalidation, so a rolled-back revocation fires nothing.

**F3. `passport:keys` uses OpenSSL instead of phpseclib.** phpseclib is used only here; Laravel uses it because `openssl_pkey_new()` is unreliable on Windows, which Swoole does not support, and `ext-openssl` is already required.

```php
$key = openssl_pkey_new(['private_key_bits' => $length, 'private_key_type' => OPENSSL_KEYTYPE_RSA]);
openssl_pkey_export($key, $privateKey);
$publicKey = openssl_pkey_get_details($key)['key'];
```

These return false on failure instead of throwing; fail with `openssl_error_string()`. Keep PEM output (PKCS#8 private, SPKI public) and the `chmod` 0600/0660. Keep `--length=4096` default.

**F4. Cookie name** `laravel_token` → `hypervel_token` (framework-name rule), via a `DEFAULT_COOKIE` constant shared with `flushState()`.

**F5. `personalAccessClient()` filters in SQL.** Upstream loads every non-revoked client for the provider (for the default provider: every null-provider client, which MCP dynamic registration creates without authentication) and filters by grant type in PHP on each `createToken()`.

```php
return Passport::client()->newQuery()
    ->where('revoked', false)
    ->whereJsonContains('grant_types', 'personal_access')
    ->where(fn (Builder $query) => $query
        ->when($provider === Passport::defaultProvider(), fn (Builder $query) => $query->orWhereNull('provider'))
        ->orWhere('provider', $provider))
    ->latest()
    ->lazy(100)
    ->first(fn (Client $client): bool => $this->allowsClient($client))
    ?? throw new RuntimeException("Personal access client not found for '{$provider}' user provider. Please create one.");
```

`allowsClient()` is H2's check, run on each candidate newest first, so the first eligible client wins when several exist (e.g. shared clients granted to different partitions); the common case is still one small query. Custom client models that store grant types differently override `personalAccessClient()`, since `hasGrantType()` no longer drives this lookup (README difference). Cover with DB-driver integration tests (grammar differs per driver).

**F6. `passport:purge` deletes in primary-key batches; `expires_at` partial indexes.**
Upstream runs one `DELETE … WHERE (revoked = true OR expires_at < ?)` per table (plus a `NOT EXISTS` active-refresh-token check for access tokens). Upstream's tables have no `revoked` or `expires_at` index, so each statement scans the whole table. On MySQL/MariaDB that blocks token writes for the whole purge: "If you have no indexes suitable for your statement and MySQL must scan the entire table to process the statement, every row of the table becomes locked, which in turn blocks all inserts by other users to the table" (https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html). Token tables grow large (every refresh adds rows; default lifetime one year) and new rows land at random positions in the random `char(80)` primary key, so token issuance, refresh and revocation all wait.
Fix, keeping the command's options and output unchanged (conditions change only as C6 requires: revoked refresh tokens are kept until they expire, and families with no refresh tokens left are deleted, in the same batches):
- For each table, select matching IDs with `chunkById()` over the primary key (same conditions as upstream, including the active-refresh-token exclusion) and delete each batch with `whereKey($ids)->delete()`. Plain selects take no locks in InnoDB ("A consistent read does not set any locks on the tables it accesses", https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html), and each delete locks only its batch's rows by primary key. Use a batch-size constant (1000).
- Add `->index('expires_at')->whereNotNull('expires_at')` to `oauth_access_tokens`, `oauth_refresh_tokens`, `oauth_auth_codes`, `oauth_device_codes` (precedent and comment: Sanctum's `personal_access_tokens` migration). Partial on Postgres and SQLite, an ordinary index on MySQL/MariaDB (Hypervel's `compileWhereNotNull()` is only used by the Postgres and SQLite grammars).
- Rejected: `limit()->delete()` loops as in `MassPrunable`. Each statement still scans until it finds a batch, and the final empty statement scans the whole table under row locks, unless every condition has an index. Hypervel's index API only supports `whereNotNull` partial indexes, so `revoked` cannot get a small partial index, and a full `revoked` index adds write cost to every token insert and revocation for no benefit over the select-then-delete approach.

**F7. `AuthCode` casts `scopes` to `array`.** `Token` and `DeviceCode` cast `scopes`; `AuthCode` does not, and `Bridge\AuthCodeRepository::persistNewAuthCode()` `json_encode()`s the scopes itself, so `$authCode->scopes` is a JSON string. Add the cast and pass `$authCodeEntity->getScopes()` (the cast encodes the scope entities through `jsonSerialize()`; stored JSON is unchanged).

**F8. The cookie JWT keeps `firebase/php-jwt`, signed with a derived key.** Upstream's `JWT::encode()` in `ApiTokenCookieFactory::createToken()` and `JWT::decode()` in `TokenGuard::decodeJwtTokenCookie()` stay, so those methods and their tests stay close to upstream. Firebase decodes and validates a cookie in about 5 µs, against 10–14 µs for lcobucci with its setup reused. That CPU time blocks the worker on every cookie-authenticated request, and the cache (E) doesn't cover it. Rejected: moving the cookie to lcobucci for a single JWT library; it is slower, rewrites the upstream methods and tests, and Firebase is already a root dependency (Socialite). Access tokens are unaffected: League signs and verifies them with lcobucci.
- Claims: upstream's `sub`, `csrf` and `exp`, plus `provider` (C2) and `bind` (H4, only when registered). `TokenGuard` checks `csrf`, `provider` and `bind` after Firebase validates the signature and `exp`.
- HMAC key: Firebase 7 rejects HS256 keys under 256 bits, so upstream fails with AES-128 app keys (16 bytes). Sign and verify with `hash_hkdf('sha256', Passport::tokenEncryptionKey($encrypter), 32, 'hypervel-passport-cookie')`; the label also keeps it independent of D1's key. `ServerFactory` derives it once per worker next to D1's key (`cookieKey()`), and the factory and the guard read it from there.

**F9. Schema.** Upstream's migrations, plus:
- `jsonb` for `scopes` (auth codes, access tokens, device codes), `redirect_uris` and `grant_types`; the `array` casts and `whereJsonContains()` work unchanged.
- `provider` on the four token and code tables (C1); `family_id` and `oauth_refresh_token_families` (C6); `oauth_signing_keys` (I4).
- An index on `oauth_access_tokens (user_id, provider, client_id)` replacing upstream's `user_id` index: it serves `tokens()` (`user_id`, `provider`) and the skip-consent check (all three). Plus a plain `client_id` index for the `Client::tokens()` relation, whose bulk writes E supports. F6's `expires_at` indexes. Other columns and indexes stay as upstream.

**F10. Named rate limiter.** Upstream's token and device-code routes use bare `throttle` (60 per minute, keyed by user or IP). Use `throttle:passport`, including the device authorization page's user-code lookup to limit guessing (RFC 8628 §5.1), and in a `booted()` callback register a `passport` limiter with the same default when the app hasn't defined one. Apps can tune it with `RateLimiter::for('passport', ...)`. Repeated user-code lookups must honor an application's limit.

**F11. `Client::revoke(): bool`.** A2 removes the deprecated `ClientRepository::delete()`, the only revocation helper. Add `revoke()` to `Client`, matching `Token::revoke()` and `RefreshToken::revoke()`: it sets `revoked` and saves, and E invalidates the cache. Its tokens stop working through `findActive()` (guard) and C7 (middleware) and are purged once they expire, so no token cleanup runs.

**F12. Retry device-code collisions without savepoints on token issuance.** Device user codes are 8 characters from a 20-letter alphabet, so collisions happen at scale. Device-code persistence translates collisions on identifiers League regenerates (the primary key or `user_code`) into `UniqueTokenIdentifierConstraintViolationException`; use a savepoint only when a caller already has a transaction open. Translation happens after rollback and checks the failing table and constraint, so unrelated or observer failures propagate. Resolve named indexes through schema metadata only on the failure path when the driver supplies no columns. Access-token, auth-code and refresh-token identifiers contain 320 random bits: save them directly and propagate database errors rather than adding savepoints to every issuance for collision recovery. A family and its first refresh token share C3's transaction; direct repository calls without an issuance use one transaction for both. Auth-code creation, device-code creation and device approval are single-statement writes and do not open an issuance transaction. All repositories still reject canceled model saves.

**F13. Consent pages can't be framed.** Upstream applies no frame protection, so the consent and device pages can be framed to trick users into approving (RFC 9700 section 4.16). Passport's authorization, device-code entry and device authorization pages get Hypervel's `FrameGuard` middleware. Framework fix: `FrameGuard` calls `headers->set('X-Frame-Options', 'SAMEORIGIN', false)`, and Symfony's `HeaderBag::set()` appends when `replace` is false, so an app's `DENY` ends up next to `SAMEORIGIN`; it now sets the header only when it's missing (Laravel has the same code). The docs suggest the same protection for app-owned login pages.

### G. Kept as upstream (considered, rejected)

- String route actions with the group `namespace` — Horizon and Telescope ports kept them.
- The static `Passport` configuration class (boot-time statics with `Boot-only.` docblocks and `flushState()`).
- `tokensExpireIn(DateTimeInterface)` etc. — they store an interval computed once, which is what the documented `now()->add…()` usage means.
- Passport's cookie serialization toggles (`withCookieSerialization()` …) — tied to the framework's `EncryptCookies::$serialize`, a separate framework question.
- RSA-4096 default key length (~3.7 ms per signature).

### H. Extension points for partitioned apps

These generic hooks let applications supply authorization policy and contextual attributes without replacing Passport internals. Tests use small application models with attributes such as `organization_id`. Hooks are static registrations like `Sanctum::authenticateAccessTokensUsing()`, each with a `Boot-only.` docblock and reset in `Passport::flushState()`.

Why checks run on loaded models: a shared token endpoint may learn an application's authorization context only from a stored code or refresh token. A query filter requiring that context before the lookup cannot cover this path. Model hooks set application-owned columns, and Passport calls back where it accepts a token, client or cookie; inherited grant attributes preserve the context across exchanges.

Invariant: every Passport read and write goes through the configurable models (`Passport::token()`, `client()`, `authCode()`, `refreshToken()`, `refreshTokenFamily()`, `deviceCode()`, `signingKey()`) and Eloquent, never `DB::table()`, so model scopes always apply. Upstream already does this; keep it, including F6's purge queries. Model events don't run for Passport's bulk writes (claims, approvals, revokes, relation writes): E and F2 handle those explicitly, and an integration that guards writes does it in the models' query builder.

**H1. `Passport::authenticateAccessTokensUsing(Closure(Token $token, bool $isValid): bool)`**: same name, signature and meaning as Sanctum's.
- Called from `Bridge\AccessTokenRepository::isAccessTokenRevoked()`. League calls that for every bearer validation (`TokenGuard`, and `ValidateToken` for `CheckToken`, `CheckTokenForAnyScope` and `EnsureClientIsResourceOwner`), so one call site covers every path.
- The method loads the token model through overridable `Token::findToken(string $id): ?static` (E's cache when enabled) instead of running `doesntExist()`. Sanctum's `PersonalAccessToken::findToken()` is the precedent: a model subclass can customize the authentication lookup independently of listing queries. `AccessToken::getToken()` uses it too. `$isValid = ! $token->revoked`; a registered callback receives `($token, $isValid)` and can only narrow it: the token is accepted when `$isValid` and the callback both say so, so a callback can't accept a revoked token. (Sanctum lets its callback decide because its `$isValid` is an expiry policy; Passport's is revocation.) A missing token is revoked without calling the callback, as Sanctum does. The token's client must also be active (C7). League turns a rejection into a 401 `access_denied`.
- Reuse E's request-scoped token memo in `AccessToken::getToken()`, so `$user->token()->expires_at` or an owner column costs no second query (upstream re-queries). Package writes that revoke by query forget the affected entries.

**H2. `Passport::authenticateClientsUsing(Closure(Client $client): bool)`.**
- Called from `ClientRepository::findActive()` after the revoked check. Every client lookup goes through it: league's `Bridge\ClientRepository::getClientEntity()` and `validateClient()` (authorize, token and device endpoints) and the guard. A rejected client is treated as not found.
- Runs on the loaded model, cached or not, and on each `personalAccessClient()` candidate (F5). Client cache keys use the global client ID. Context-prefixed copies of a shared client would complicate invalidation: revoking it must invalidate every use of the same row.

**H3. `Passport::inheritGrantAttributes(array $attributes)`.**
- Tokens issued from an authorization code, device code or refresh token copy these attributes from it (e.g. `['organization_id']`). Needed when the token endpoint doesn't know the owner (one OAuth host for every organization): the owner chosen at authorization reaches the tokens and every later refresh.
- Passport always carries `provider` (C1) and, on refresh tokens only, `family_id` (C6). `provider` and the registered attributes go on new access and refresh tokens; the registered attributes also go on a new family row. C3's read-only checks (`isAuthCodeRevoked()`, `isRefreshTokenRevoked()`, `getDeviceCodeEntityByDeviceCode()`) record the redeemed row in the issuance context, and `persistNewAccessToken()`, `persistNewRefreshToken()` and the family insert apply the values before saving, so model `creating` hooks see them.
- Queries: each redeemed row is read once, with these columns and `revoked`, in place of upstream's `exists()` check, so there's no extra query.
- Issuance context: `Bridge\TokenIssuance` holds the state of one issuance: the redeemed row and its attributes, J1's authorization attributes, C3's claim and transaction, the saved access token (J1, J6), a personal access token's name, and the server entry in use (I1). `Bridge\AuthorizationServer` (token requests, also used as the personal-access server) and the consent-completion calls (approve controllers, automatic approval) each start a fresh one and restore the previous one in `finally`, so a nested issuance (e.g. a listener creating a personal access token during an exchange) or several in one job never share state. It lives in `CoroutineContext` under `__passport.issuance`.
- `PersonalAccessGrant` records the token name in the issuance context and `persistNewAccessToken()` saves it in the same insert, replacing upstream's separate update (one query fewer, and the saved model stays current).
- Personal access tokens get `provider` from `PersonalAccessTokenFactory` (C1). Otherwise personal access and client-credentials tokens have no source grant, and model hooks set their attributes.

**H4. `Passport::bindCookiesUsing(Closure(Request $request): ?string)`.**
- `ApiTokenCookieFactory` stores the returned value in the cookie's `bind` claim; the guard's cookie path rejects a cookie whose claim differs from the value for the current request (null matches null).
- This lets an application bind cookie authentication to its current authorization context even when cookie paths or domains are shared. Cookie transport scope alone does not express that policy.

**H5. The cookie follows the session cookie's per-request attributes.** Upstream's `ApiTokenCookieFactory` copies static `session.*` config, but session cookie attributes are resolved per request by `StartSession::configureSessionCookieUsing()` callbacks. Applications may narrow the domain or set `partitioned` or `secure`. The public static `StartSession::resolveCookieConfig(Request $request, array $config): array` is shared by `StartSession::addCookieToResponse()` and `ApiTokenCookieFactory::make()`; it replaces the protected `resolveSessionCookieConfig()`. Logout needs the same attributes: upstream's `Logout` listener queues `Cookie::forget()` with static defaults, so with a narrowed domain (an empty string for host-only) it expires a different cookie and the real one keeps authenticating. `ApiTokenCookieFactory::forget(): Cookie` reads the current request like `make()` and builds the expired cookie with the resolved path, domain, secure, SameSite and partitioned values (built directly, because `CookieJar::forget()` treats an empty domain as missing), and the listener queues it.

**H6. `TokenGuard::token(): ?AccessToken`** returns the current request's validated access token (bearer path; null for cookie authentication), built from B1's cached attributes. Client-credentials requests have no user, so `$request->user()->currentAccessToken()` cannot reach their token. Middleware and application policy can inspect it through the guard instead.

### I. Per-request server settings, key IDs and key rotation

**I1. `ServerFactory` builds league servers per settings set.**
Why: applications serving multiple authorization contexts need to select signing keys, scopes and token lifetimes per request while reusing configured servers. Upstream builds one `AuthorizationServer` and `ResourceServer` from global statics.

```php
interface ServerSettingsResolver
{
    /**
     * Return the identifier of the current request's settings, or null for the default settings.
     *
     * Called on every OAuth request, so it must not query the database. It must change whenever the settings change.
     */
    public function current(): ?string;

    /**
     * Load the settings for an identifier returned by current().
     */
    public function resolve(string $identifier): ServerSettings;
}
```

- `Contracts\ServerSettingsResolver` is an optional container binding; unbound means default settings only.
- `ServerSettings` (readonly value object): `keys` (list of `ServerKey`), `tokensExpireIn`, `refreshTokensExpireIn`, `personalAccessTokensExpireIn`, `clientCredentialsTokensExpireIn` (`?DateInterval`; null uses `Passport::*ExpireIn()`), `scopes` (`array<string, string>` added to `Passport::$scopes`), `issuer` (`?string`, J3).
- `ServerKey` (readonly value object): `publicKey`, `?privateKey` (null: verify only), `?activatesAt` (null: active from the start); keys are PEM or a path, as `CryptKey` accepts. The signing key is the newest key with a private key whose `activatesAt` is null or past; every key verifies. Verification needs public keys only, so a service that only checks tokens can supply public keys alone; issuing without a signing key fails.
- Default settings come from the configured key store (files by default, or I4's database store) and the global statics.
- `ServerFactory` (auto-singleton) exposes `authorizationServer()`, `personalAccessServer()`, `resourceServer()` and `settings()` (J2 adds `signingKey()` and `jwks()`). An entry holds the settings and lazily built servers: the main server with all grants (C5's auth-code grant and B4's device grant included), the personal-access server, and one resource server whose validator holds every verification key (D5, I2). The default entry lives in a property; resolver entries live in an LRU array like `RulePlanCache`, capped by `passport.server_cache_size` (default 1000 in shipped config). The docs explain the trade-off (memory per worker against rebuilds), so operators can change it. Eviction only costs a rebuild (~1 ms of key parsing). An issuance selects its entry and signing key when it starts and pins both in the issuance context (H3), without writing anything; `settings()`, `signingKey()` and `jwks()` return them for the rest of the issuance, so an activation boundary or settings change mid-request can't mix signing keys or settings. The main and personal-access servers are `Bridge\AuthorizationServer` (C3); resource servers use D5's validator. Instance state on an auto-singleton: no static, no `flushState()`. Rejected: worker key caches with expiry and app-wired invalidation between workers; `current()` changes whenever keys or settings change, so outdated entries are never used and age out of the LRU.
- Move the provider's server-building methods (`makeAuthCodeGrant()`, `buildAuthCodeGrant()`, `makeRefreshTokenGrant()`, `makeDeviceCodeGrant()`, `makeAuthorizationServer()`, `makeCryptKey()`) to `ServerFactory` as protected methods that take the `ServerSettings`. D1's `Key` is app-wide and built once.
- Consumers resolve per request: `AccessTokenController`, `AuthorizationController`, `ApproveAuthorizationController`, `DenyAuthorizationController`, `DeviceCodeController`, `ApproveDeviceAuthorizationController`, `DenyDeviceAuthorizationController` and `PersonalAccessTokenFactory` call `authorizationServer()` or `personalAccessServer()`; `TokenGuard` and `ValidateToken` call `resourceServer()` (D3).
- `AuthorizationServer::class` and `ResourceServer::class` stay resolvable for app code. Held instances delegate request entry points to the current settings' server, so constructor-injected consumers survive rotation and settings changes. Token requests start a fresh issuance before selecting the signing server; device-code creation also gets a fresh context. Consent controllers retain their attribute-carrying contexts around upstream protected methods; completion uses that context or starts one for a direct call. Authorization validation opens no transaction. Delegation invokes the selected server's parent operation directly, without repeated selection. Resource validation remains PSR-native and fresh for direct callers; guards and middleware retain B1's shared memo.
- `Passport::actingAsClient()` places its resource-server mock in coroutine context. `ServerFactory::resourceServer()` checks this override first, so guards and middleware already holding the factory see subsequent calls. Simulated HTTP requests inherit the override from the test coroutine; no factory replacement or additional durable auth key is needed.
- Scopes: `Passport::scopes()`, `scopeIds()`, `hasScope()`, `scopesFor()` and `validScopes()` read `static::$scopes` plus `settings()->scopes` when a resolver is bound (no extra work otherwise). `Passport::$scopes` and `tokensCan()` stay the global catalog (MCP adds to it at boot).

**I2. Access tokens carry a `kid` header.**
- Key ID = the RFC 7638 JWK thumbprint of the public key (SHA-256 over the canonical `{"e","kty":"RSA","n"}` JSON, base64url), computed when an entry is built. The deterministic value also appears in `ServerFactory::jwks()` for application-defined key-set endpoints.
- Signing: `Bridge\SigningCryptKey extends CryptKey` carries the key ID. `ServerFactory` picks the signing key when an issuance starts and pins it (I1), caching one authorization server per signing key ID, giving it the key as the private key; league passes it to each access token (`setPrivateKey()`); `Bridge\AccessToken::convertToJWT()` replaces the trait's private method (copy league's builder chain) and adds `->withHeader('kid', ...)`.
- Verification: `Bridge\BearerTokenValidator` (D5) reads `kid` from the parsed token's header and verifies with that key from its map. An unknown `kid` is rejected without a signature check or a key reload (a reload would let anyone force database reads). A token without `kid` (only Laravel-issued tokens lack one, since every Hypervel token carries it) is tried against the retained keys, newest first; each try costs tens of microseconds with parsed keys, and how many keys are retained depends on lifetimes and rotation (one-year tokens with 90-day rotation keep about five). The guard, the token middleware and the container's `ResourceServer` all use this validator.
- `Bridge\AccessToken` memoizes the string from `toString()`. League calls it once per response, but a second call (OpenID Connect's `at_hash`, J) would sign again (~3.7 ms) and can produce a different token. The setters that change its claims or key (`setIdentifier()`, `setExpiryDateTime()`, `setUserIdentifier()`, `setClient()`, `addScope()`, `setPrivateKey()`) clear the memo.
- `Bridge\AccessToken` also keeps the saved `Token` model, set by `persistNewAccessToken()`, which J5's claims and custom response types read without a query.
- RSA only (league's signer).

**I3. Key rotation.**
- Rule: publish a key before signing with it. (1) Add the new public key as verify-only. (2) Once every worker and instance has it, sign with it and keep the old public key verify-only. (3) Remove the old key after the longest token lifetime it signed (personal access tokens default to one year). Codes and refresh tokens are encrypted with the app key, so RSA rotation doesn't affect them.
- Database store (I4): the steps happen automatically, with no restarts.
- Files store (the default): the operator rotates in their secret manager, using `passport.verification_keys` for verify-only keys. Servers live for the worker lifetime, so each step needs a full restart of the server and every long-running process that issues or checks tokens (queue workers, custom processes); `server:reload` is not enough. Rolling restarts follow the same three steps. With the files store, `passport:keys` prints the same restart warning as `hypervel/jwt`'s key commands. Laravel reads key files per request, hence a porting-guide entry.
- Resolver-based apps: a rotation reaches every worker and instance when `current()` changes. The delay depends on the freshness of its backing state and any application cache; `passport.key_activation_delay` must be longer, and an emergency key removal takes effect within the same delay.
- Per-request settings must be known before OAuth processing, for example from a trusted host, path or header mapping. Passport does not discover a settings set from an unverified token's `kid`. Without a resolver-selected set, validation uses the default keys.

**I4. Database key store (opt-in).**
Why: apps can rotate keys without restarts or logouts, on a schedule or after a suspected leak, and keys reach every instance through the database. Files stay the default for Laravel parity: `passport:keys` writes files, `PASSPORT_PRIVATE_KEY` / `PASSPORT_PUBLIC_KEY` keep working (including keys from a secret manager), and app tests can use stored key files instead of creating keys in each test. Encrypting with the app key protects against leaks of the database alone, such as backups or dumps; anyone with both the database and the app key can decrypt the stored keys.

Encrypted signing-key storage has public precedents: [Ory Hydra's SQL key store](https://github.com/ory/hydra/blob/4174065ffb052799890f7480f5360a877a67ffc1/persistence/sql/persister_jwk.go) encrypts JWKs with AES-GCM before persistence. [Duende IdentityServer's automatic key management](https://docs.duendesoftware.com/identityserver/fundamentals/key-management/) protects keys with ASP.NET Core Data Protection by default and supports file and database stores. These precedents support the storage model; Passport uses Hypervel's existing encryption facilities.

- Config (`config/passport.php`, "Encryption Keys" section): `key_store` (`env('PASSPORT_KEY_STORE', 'files')`, or `database`; backed enum `Enums\KeyStore`); `private_key`, `public_key`, `verification_keys` (files store); `key_activation_delay` (seconds, default 86400) and `key_refresh_interval` (seconds, default 60); `key_rotation.enabled` (`env('PASSPORT_KEY_ROTATION', true)`, cast to bool) and `key_rotation.days` (`env('PASSPORT_KEY_ROTATION_DAYS', 90)`, cast to int). Defaults live only in shipped config. Boot validation (console `booted`, server `AfterWorkerStart`, like E): with the database store, `key_activation_delay` must exceed `key_refresh_interval`.
- Table `oauth_signing_keys`: `uuid('id')->primary()`, `text('public_key')`, `text('private_key')->nullable()` (null for verify-only keys brought in by `passport:keys:import`), `dateTime('activates_at')`, `unsignedBigInteger('max_token_lifetime')->default(0)` (seconds, allowing long configured lifetimes without integer overflow), `dateTime('retain_until')->nullable()`, `dateTime('retires_at')->nullable()` (prune hint), timestamps. Model `SigningKey` (`HasUuids`, `HasFactory`, `encrypted` cast on `private_key`), swappable through `Passport::useSigningKeyModel()` / `signingKeyModel()` / `signingKey()` like the other models. `app.previous_keys` keeps keys readable after an app key rotation.
- States come from timestamps, so no job switches keys: the signing key is the newest with `activates_at` in the past; newer keys only verify; older keys verify until pruned. Every worker and instance agrees as long as each loaded the new key before it activates, which the activation delay guarantees.
- `SigningKeyRepository`, used by the commands and application integrations: `create()` (signs immediately), `rotate()` (signs after the activation delay), `rotateDueKeys()` (rotates when the signing key activated more than `key_rotation.days` ago and no newer key is waiting, then prunes; apps with many key sets override it), `prune()`, `revoke(string $keyId)`, `import(string $privateKey)`, `importFiles(?DateTimeInterface $retainUntil = null)`, `all()`; creation takes a key length (default 4096, generated as in F3). `import()` takes a supplied PEM, rejects anything but an RSA key of at least 2048 bits, derives the public key and queues it to sign `key_activation_delay` after the later of now and any waiting key's activation. Swapping keys at once would break workers that haven't loaded the new key; the old public key also remains available for tokens it signed. `rotate()` and `rotateDueKeys()` prune replaced keys whose retention has passed (Retention below). Settings projections expose private keys only for the signing key and newer keys; older keys enter `ServerSettings` as verify-only.
- `all()` returns signing-key models; `serverKeys()` supplies settings-ready keys that retain their database row identity and loaded retention bound. Custom settings resolvers use this projection so signing updates the correct row without another lookup. Plain file/config keys require no retention writes. An import rejects a thumbprint already in the set under the set lock; `importFiles()` deduplicates its inputs by thumbprint, keeping the signing copy when also listed for verification.
- Retention. Each key has two values that are only ever raised: `max_token_lifetime` (seconds) and `retain_until` (a nullable floor, set by `importFiles()`). A key that a newer active key has replaced can be deleted once both `retain_until` and its successor's `activates_at` plus `max_token_lifetime` have passed. A key is active when an issuance pins it, so its successor activates no earlier than the pin.
- Retention writes happen only when a key actually signs, inside C3's issuance transaction after validation, never when an issuance pins its key and never on bearer or key-set requests. The needed bound is the larger of the token's lifetime converted conservatively (366-day years, 31-day months) and the seconds from the pin to the token's actual expiry, rounded up; since the successor activates after the pin, its `activates_at` plus that bound covers the expiry even when the successor was published during the issuance. J2's `signingKey(DateInterval $lifetime)` does the same with the expiry at the time it's called. When the needed bound exceeds the worker's copy, one conditional update raises it (`where max_token_lifetime < needed`). If that updates nothing, an authoritative read tells a bound that's already high enough (another worker raised it; fine) from a missing key (pruned meanwhile; the issuance fails rather than emit an unverifiable token). The worker raises its in-memory copy only after commit, keeping the larger value, so a rolled-back issuance can't hide a needed raise. Ordinary issuances finish within the bound already recorded, so this writes rarely.
- `retires_at` is only a hint for finding prune candidates (estimated when a successor is added, refreshed by prune). `prune()` runs under the set lock, recomputes each candidate's deadline from writer rows, and deletes with a condition matching the values it read, so a concurrent raise or an early hint can't remove a key that's still needed. Retention raises leave key material unchanged, and pruning removes only replaced keys past their retention deadlines. Both use query writes without model events; valid-token verification does not require a resolver's `current()` identifier to change for them. Creation and emergency revocation fire model events so an integration can update that identifier's backing state atomically with the key changes.
- `importFiles()` sets each imported key's `retain_until` to the later of the latest `expires_at` among stored access tokens and `$retainUntil` (for tokens or lifetimes Passport can't discover, such as other issuers using the same keys); the command takes `--retain-until=`. Seed the imported signing key's `max_token_lifetime` with the longest configured access, personal-access or client-credentials lifetime, using the same conservative conversion as signing-time retention. This also retains tokens that file-store workers issue between import and restart. Verify-only imports keep the expiry/explicit floor without this seed.
- Management mutations (`create()`, `rotate()`, `import()`, `revoke()`, `prune()`) are atomic and serialized. Each runs under one cache lock named for the set (`passport:signing-keys:{name}`, where `SigningKeyRepository::keySetName()` returns `default` unless an integration overrides it), which also covers an empty set. RSA material is generated before taking the lock (only when it will be needed), the state is rechecked inside, and the writes happen in one transaction on the writer, including any integration's model-event updates to the state behind `ServerSettingsResolver::current()`. Waiting keys activate in order and are never replaced or cancelled by routine mutations, because a worker may already be about to sign with a published waiting key: a new key activates `key_activation_delay` after the later of now and the newest waiting key's activation. `rotate()` returns the newest waiting key if there is one (checked before generating and again under the lock). `revoke()` is the emergency path: it inserts the replacement (active at once) and deletes the revoked key in the same transaction, so the set always keeps a signing key, and it accepts brief failures elsewhere (documented). `create()` does nothing when the set already has keys. They refuse to run inside an app transaction (`hasApplicableTransaction()`, which ignores the test-wrapping one), checked before generating anything, so the lock is held until the writes really commit. Retention raises don't take this lock: they join the issuance and rely on conditional updates and prune's compare-and-delete. The lock needs a cache store with atomic locks shared by all instances, as `onOneServer()` does.
- Commands:
  - `passport:keys`: the files store (default) writes files as upstream (F3); the database store creates the first key, signing immediately, and refuses when keys exist, pointing to `passport:keys:rotate`. `--force` keeps its upstream meaning for files.
  - `passport:keys:rotate {--due} {--length=4096}`: rotates now; with `--due` it calls `rotateDueKeys()`. Distinguish a newly published key from one already waiting. Refuse with the files store and point to manual rotation through `verification_keys`.
  - `passport:keys:revoke {kid}`: deletes the key; if it was signing, creates a replacement that signs immediately. Return failure for an unknown key or the files store. Tokens it signed stop working, and other workers pick up the replacement within the refresh interval, so a few tokens can fail briefly elsewhere (acceptable in an emergency; documented).
  - `passport:keys:import {--retain-until=}`: copies the files store's keys into the database (the signing key active at once, `verification_keys` as older keys), so an app can switch to the database store without logging users out.
  - `passport:keys:list`: key ID, created, activates, retires, and whether it signs, waits or only verifies.
- Scheduled rotation: with the database store and `key_rotation.enabled`, `PassportServiceProvider` schedules `passport:keys:rotate --due` daily through `callAfterResolving(Schedule::class, ...)`, with `onOneServer()` so instances don't rotate twice and `withoutOverlapping()`. Apps don't set up the schedule themselves; the scheduler just has to run. The files store has no schedule, since its keys are managed outside the app.
- `ServerFactory`'s default entry with the database store reloads the key rows once `key_refresh_interval` has passed since the last load (one small query per worker per interval) and rebuilds only when the set of key IDs changed. Activation needs no reload.
- `passport:install`: with the files store it runs as upstream (`passport:keys` first); with the database store it runs `passport:keys` after migrating, and if the user skips migrations, it prints the command to run afterwards.
- Testing: `SigningKeyFactory` generates one 2048-bit pair per test process and reuses it. Its static key gets a `flushState()` that is not registered in `AfterEachTestSubscriber` (an immutable test key can't leak state, and regenerating per test would be slow). The docs tell apps using the database store to call `SigningKey::factory()->create()` in tests that issue tokens. Passport's own suite uses the factory for database-store tests and the per-process key pair in `ParallelTesting::tempDir()` for files-store tests.

### J. OpenID Connect readiness

These extension points support OpenID Connect implementations without replacing Passport's grant and controller internals. Authorization attributes carry values such as `nonce` and `auth_time` through consent and token issuance, avoiding an extension's need to decrypt and rewrite authorization codes. Issuance hooks do not run during bearer validation; an unused hook costs a null check. Discovery documents belong to the implementing extension or application and can use Passport's route names, `Passport::scopeIds()` and the settings issuer. Passport itself registers no discovery route.

Public implementations illustrate the missing extension points:

- [`ronvanderheijden/openid-connect`](https://github.com/ronvanderheijden/openid-connect/blob/8a0ecd9b43c1e8e21dadb9634aeed25055c9bed0/src/Grant/AuthCodeGrant.php) decrypts the code in the authorization redirect, adds a nonce from the current request and re-encrypts it. That cannot recover the original nonce when a later consent submission omits it. Its [ID-token response](https://github.com/ronvanderheijden/openid-connect/blob/8a0ecd9b43c1e8e21dadb9634aeed25055c9bed0/src/IdTokenResponse.php) decrypts the code again at exchange.
- Limosa's [OpenID Connect grant](https://github.com/limosa-io/openid-connect-server/blob/86f33aca6d15dd792e186642b2fbbb4543389fee/src/Grant/AuthCodeGrant.php) and [Passport authorization controller](https://github.com/limosa-io/laravel-openid-connect-server/blob/91beee656b50fa13130d5047cc67b7b6dd0ef60c/src/Http/Controllers/AuthorizationController.php) override the corresponding upstream flows; the grant also decrypts the code again after the parent exchange. Stored authorization attributes and response hooks avoid that duplication.

**J1. `Passport::authorizationAttributesUsing(Closure(Request $request, Authenticatable $user): array)`.** Values for the authorization being approved (OpenID Connect: `nonce`, `auth_time`, `acr`, `amr`, the `claims` request). Passport uses the same path for its own `provider` attribute (C1), so the path runs even with no callback registered.
- `AuthorizationController::authorize()` calls it once the user is known and passes the values on: directly to `approveRequest()` for automatic approval, or in the session next to `authRequest` for the consent screen (read back by `ApproveAuthorizationController`). The controller completes the request inside a fresh issuance context carrying them (H3), and `Bridge\AuthCodeRepository::persistNewAuthCode()` adds them to the same insert. Device flow: `DeviceAuthorizationController` stores them with `deviceCode` in the session, and `persistDeviceCode()`'s approval update includes them.
- H3 carries them to tokens and refreshes; the package that registers them adds the columns and decides which apply to refreshes (OpenID Connect leaves `nonce` out of refreshed ID tokens).
- `persistNewAccessToken()` also keeps the saved model on the access token entity and in the issuance context (not in H1's lookup memo, which stays out of transactions, E), so the token response reads the values from the issued token without a query or a second decryption.

**J2. Signing key and key set.** `ServerFactory::signingKey(DateInterval $lifetime): SigningCryptKey` returns the signing key of the current issuance (pinned, I1) with its key ID, for ID tokens and later logout tokens, after raising the key's retention bound to cover `$lifetime` (I4); `ServerFactory::jwks(): array` returns the RFC 7517 key set for the current settings (`kty`, `use: sig`, `alg: RS256`, `kid`, `n`, `e`), built once per cache entry from the values I2's thumbprint already extracts.

**J3. Issuer.** `ServerSettings::$issuer` (`?string`), defaulting to the new `passport.issuer` config (`env('PASSPORT_ISSUER')`, null by default). When set, `Bridge\AccessToken::convertToJWT()` adds `iss`, which outside APIs need when they verify tokens through the key set. Null keeps upstream's claims.

**J4. `Passport::resolvePromptsUsing(Closure(Request $request, AuthorizationRequestInterface $authRequest): array)`.** Returns extra `prompt` values the request needs, so Passport's existing `prompt` handling does the work: `login` for OpenID Connect's `max_age`, `id_token_hint` and `acr_values` (step-up login), `consent` for newly requested claims or `offline_access`. It may throw an `OAuthServerException` to reject parameters (e.g. OpenID Connect rejects `prompt=none` combined with other values, which Passport would otherwise reduce to `none`).
- `AuthorizationController::authorize()` calls it right after league validates the request and before Passport normalizes `prompt`.
- When the request's `prompt` contains `none`, a returned `login` throws `OAuthServerException::loginRequired()` and a returned `consent` throws `consentRequired()`. Otherwise the values join the request's prompts: `login` takes the existing logout and `promptForLogin()` path, guarded by the `promptedForLogin` session flag so it can't loop; `consent` skips automatic approval.

**J5. `Passport::accessTokenClaimsUsing(Closure(Token $token): array)`.** Extra access token claims (e.g. `client_id`, organization, roles) for outside APIs that verify tokens through the key set; demand shown by `corbosman/laravel-passport-claims`. The callback receives the saved `Token` model (I2), so claims can use `provider`, partition columns or authorization attributes without a query. Applied in I2's `convertToJWT()` at issuance only; validation is unchanged. Reserved claims (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `jti`, `scopes`) throw `InvalidArgumentException`, since validation and H1 depend on them.

**J6. `Passport::issueRefreshTokensUsing(Closure(Token $accessToken): bool)`.** OpenID Connect usually ties refresh tokens to `offline_access` (Core section 11 also allows other uses), and apps may want none for some clients. For code and device exchanges, false means no refresh token. For a refresh exchange, false rejects the refresh with `invalid_grant` and leaves no new rows or events (C3, C6), so OpenID Connect can end renewal, e.g. at an absolute session limit from the original `auth_time`, without access tokens outside a family. League asks `RefreshTokenRepositoryInterface::getNewRefreshToken()`, which takes no arguments, right after persisting the access token, and issues no refresh token when it returns null. `persistNewAccessToken()` records the saved token in the issuance context; for a code or device exchange `getNewRefreshToken()` returns null when the callback returns false, and for a refresh it throws `invalid_grant`.

**Response types.** `useAuthorizationServerResponseType()` stays the way to add response fields such as an ID token. A custom response reads the authorization data (e.g. `nonce`, `auth_time`, inherited through refreshes by H3) from the saved `Token` model on the access token entity (I2), and the exact serialized access token for `at_hash` from the entity's memoized `toString()`. It runs inside C3's transaction, so a failure rolls the issuance back. A small OpenID Connect-like response in Passport's tests covers this, including `auth_time` and `nonce` across consent and refresh.

## Public differences (README and porting guide)

The README's `Differences From Laravel` and the porting guide cover only these. Bug, security and performance fixes, internal changes and additions are described in their decisions and the feature docs.

Removed: A1 to A3 (implicit and password grants; the deprecated JSON API, repository methods and relations; pre-13 schema helpers and `passport:hash`).

Changed signatures (matter to subclasses and direct construction):
- `TokenGuard` constructor (`$name`, no `Request`), `setRequest()` removed, protected helpers take the request; `PassportServiceProvider::makeGuard()` gains `$name`.
- `CreateFreshApiToken`: `$guard` property removed, protected methods take `?string $guard`.
- `ApiTokenCookieFactory` takes the server factory and auth/request dependencies instead of an encrypter; protected `createToken()` gains a required nullable provider argument. `make()` gains optional `?string $guard` (additive); `forget()` is new (C2, H5).
- `Bridge\ClientRepository` constructor loses `Hasher`.
- `HandlesOAuthErrors::withErrorHandling()` and `Exceptions\OAuthServerException::__construct()` lose `$useFragment`.
- The controllers listed in I1, `PersonalAccessTokenFactory`, `TokenGuard` and `ValidateToken` take `ServerFactory` instead of `AuthorizationServer` / `ResourceServer`; `AuthorizationController` and `DeviceAuthorizationController` take `AuthManager` and the config `Repository` instead of `StatefulGuard` (B6), and the four approve and deny controllers also take them (C8). Custom controllers using the session-retrieval traits also need `ResolvesApprovingGuard` and its auth, config and client-repository dependencies.
- The server-building protected methods move from `PassportServiceProvider` to `ServerFactory` (I1).
- `HasApiTokens::tokens()` and `Client::tokens()` return `TokenRelation`, and `oauthApps()` returns `ClientRelation` (subclasses of `HasMany` / `MorphMany`, E).
- `ClientRepository::personalAccessClient()` filters grant types in SQL, so a client model's `hasGrantType()` override no longer drives it; override the repository method instead (F5).

Changed defaults: `actingAs()` / `actingAsClient()` guard `'passport'`; `Passport::$cookie` `hypervel_token`; routes use `throttle:passport` (F10).

Behavior porters must account for: tokens record their user provider and only guards of that provider accept them (C1); a client's `provider` restricts who can authorize it (C4); PKCE requires `S256` (C5); refresh-token reuse revokes the grant, so clients must not refresh concurrently, and rotation can only be turned off for confidential clients (C6); client secrets are stored as sha256 (D2); codes and refresh tokens use a `Key` derived from the app key, so Laravel-issued ones can't be decrypted (D1); key files and `PASSPORT_*_KEY` values are read once per worker (I3); the schema differs (`jsonb`, `provider`, refresh-token families; F9); the token endpoint can't run inside an app database transaction, and the models it writes must share one connection (C3).

Added (feature docs, not the README): H1–H6, I1–I4 (`ServerSettingsResolver`, `ServerSettings`, `ServerKey`, `ServerFactory`, `Token::findToken()`, `SigningKey`, `SigningKeyRepository`, the `passport:keys:*` commands, `passport.key_store`, `passport.verification_keys`, `passport.key_activation_delay`, `passport.key_refresh_interval`, `passport.server_cache_size`, `passport.key_rotation`), and J (`authorizationAttributesUsing()`, `resolvePromptsUsing()`, `accessTokenClaimsUsing()`, `ServerFactory::signingKey()` / `jwks()`, `passport.issuer`, `issueRefreshTokensUsing()`), plus `Client::revoke()` (F11) and `RefreshTokenFamily` with its model methods (C6).

Porting guide (`src/docs/porting-from-laravel.md`, new `### Passport` under "Other API Differences" near Fortify/JWT; high signal, link to `passport.md`): Hypervel ships a `passport` guard (Laravel's docs use `api`): `actingAs()` / `actingAsClient()` default to it and personal access clients without a provider use its provider, while other guard names still work for routes; implicit/password grants removed (use auth code + PKCE, device grant, Sanctum or JWT); deprecated JSON API and methods removed; cookie renamed; after migrating, users re-authorize (refresh tokens, auth codes) and confidential client secrets must be regenerated; `CreateFreshApiToken` subclasses must update overrides; clients using PKCE `plain` must switch to `S256` (C5); key files and `PASSPORT_*_KEY` values are read once per worker, so restart after changing them (I3); tokens store their user provider and the schema differs (`jsonb`, `provider`, refresh-token families), so use Hypervel's migrations and set `provider` on imported token rows (C1, F9); clients must not refresh concurrently with the same refresh token (C6); the token endpoint can't run inside an app database transaction (e.g. transaction-per-request middleware), and the token, code and refresh-token models must share one connection (C3).

## Related documentation consistency

JWT documentation uses the shipped `jwt` guard alongside `sanctum` and `passport`, rather than instructing applications to configure a duplicate `api` guard. Its examples use `Auth::guard('jwt')`, `auth:jwt` and `AUTH_GUARD=jwt`; the porting guide maps `jwt.auth` middleware to `auth:jwt`. Generic custom-driver examples, API URL paths and the `api` middleware group retain their distinct meanings.
