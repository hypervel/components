# Recycle server workers from the booted application

## Operator contract

Keep Hypervel's pre-fork bootstrap. Rename `server:reload` to `server:recycle-workers` and remove the automatic worker-start rebuild of dotenv and configuration. The replacement worker inherits the server's booted application, starts its own worker lifecycle, and can reclaim memory and other state accumulated in the old worker. This applies to manual recycling, request-count turnover and crash recovery. Applications can still run their own worker-start listeners and read files explicitly. Deploy code, configuration and key changes by gracefully restarting the server. Use rolling instances when a deployment must keep accepting traffic.

The previous behavior did refresh some settings. It did not rerun providers or rebuild the classes, compiled routes, listeners or resolved services that had already consumed them. After editing an environment value and killing just one event worker, its replacement read the new configuration while its provider-created service retained the old value. The surviving worker still read the old configuration. Nobody issued a reload. With just the framework refresh removed, both workers agreed with their booted services. A bad edit could also put replacements into a crash loop. Document this reason for dropping live config refresh in the PR.

## Why keep the pre-fork app

Laravel Octane launches a separate Swoole entry point, constructs native tables before fork and boots the app in each worker. Hypervel's `Server::initServers()` resolves configured handlers through the container. The HTTP handler warms the router before fork. Providers and applications use pre-fork events for shared tables, locks and custom processes, including container-resolved process instances. A fresh worker app alone cannot replace code loaded in the manager or recreate those shared resources. Rebooting the existing container in a forked worker would still inherit all loaded PHP declarations.

The relevant Octane paths are `bin/swoole-server` and `src/Swoole/Handlers/OnWorkerStart.php`. In Hypervel, compare `ServerStartCommand::startServer()`, `Server::registerSwooleEvents()`, `HttpServer\Server::bootstrapForServer()` and `ServerProcess\Listeners\BootProcessListener`.

The comparison used PHP 8.4.28, Swoole 6.3.0 and shared CLI OPcache with JIT off. The prototype booted the real Hypervel HTTP kernel in each worker, injected the same pre-fork cache and rate-limiter tables, and exercised the real request handler. The throughput measurements cover the HTTP path. Measurements used 32 HTTP/1.1 keep-alive clients, separate client/server CPU sets, warmed requests and alternating runs. Memory is summed Linux proportional set size for the server process tree, counting shared pages proportionally.

| Case | Current pre-fork boot | Per-worker boot |
| --- | ---: | ---: |
| 8 workers, 1,000 cached routes, first generation | 114 MiB | 176 MiB |
| Same workload, after two worker recycles with warm OPcache | 111 MiB | 109 MiB |
| 8 workers, 1,000 uncached routes, after two recycles | 111 MiB | 144 MiB |
| Same uncached workload, plus a 3.8 MiB read-only map built by a provider | 114 MiB | 172 MiB |
| 8 workers, 1,000 cached routes, requests per second | 22.7k | 23.0k |
| Same cached workload, signal to all workers reporting ready | 31 ms | 103 ms |

Steady request throughput was similar with working shared OPcache. Cold parallel boots cost memory, some of which disappears when replacement workers use warm opcodes. PHP objects and arrays built by providers can still cost memory per worker. Copy-on-write lets the current workers share untouched boot state. The prototype bypassed the Artisan launcher, so its cold-start time is not an end-to-end deployment comparison.

Two real in-place edits updated the route, listener and eager config snapshot with per-worker boot and timestamp validation at `revalidate_freq=0` with changed modification times. The default two-second revalidation interval still served old PHP in this long-running CLI process even after waiting beyond it. With timestamp checks disabled, a reset at reload left the restart pending and both generations used the old opcodes. Octane's default reset from the **first** worker start let edits appear, but the application scripts stayed uncached. On the small four-worker fixture that cost **100 → 143 MiB**, **176 → 194 µs of server CPU per request**, **21.1k → 19.5k requests/s** and **31 → 123 ms** to recycle. New immutable release directories worked for app files with a fresh worker autoload root. They still leave pre-fork code and server resources tied to the server generation and impose a deployment layout. These results do not justify a second boot mode or per-provider refresh hooks.

## Implementation

1. **Rename the command and simplify delivery.** Move the command and its test to `ServerRecycleWorkersCommand` and `ServerRecycleWorkersCommandTest` following the package convention. Update the Symfony attribute, Artisan signature, registration, output and help (“Gracefully replace the server's event and task workers.”). Retain PID-file parsing, positive PID validation, the signal failure exit status and its test seam. Send **one** `SIGUSR1`. Swoole's manager adds both the event and task worker pools to this reload. `SIGUSR2` requests a task-only reload. A native check with two event workers and one task worker confirmed one signal replaced all three in PROCESS and managed BASE mode. Remove the task-count read and the extra signal branch. Report that recycling was requested once the signal was delivered. Delivery is asynchronous. Single-process BASE (one event worker, zero task/custom processes and unlimited requests) has no manager to replace the worker. State this limit in the server guide. The separate CLI process cannot infer the running topology reliably from configuration on disk.
2. **Separate deployment from manual recycling.** Remove Hypervel's built-in `server` entry from `ReloadCommand::getReloadTasks()`. Laravel's `reload` signals queue workers, interrupts the scheduler and runs package-registered tasks so services can pick up a deployment. Recycling HTTP workers would leave them serving the old app. Keep the upstream API, package tasks and `--except` semantics. Deployments should gracefully restart the server through their process monitor, or roll instances. For operational recycling, switch scripts from `server:reload` to `server:recycle-workers`. There is no legacy alias or built-in server task to exclude.
3. **Remove the disk refresh at its source.** Delete `ReloadDotenvAndConfig` and its Foundation registration. Simplify `LoadConfiguration::bootstrap()` to one initial repository, retaining config-cache selection, base/override merging, the Testbench subclass hooks and environment/timezone initialization. Remove the worker-rebuild-only previous-repository copy/rollback once its callers and tests have been reconciled. Keep `DotenvManager::reload()` for Horizon and dotenv provenance for Doctor. Preserve `WorkerStartCallback` ordering and the stdout logger's refresh of its **in-memory** settings after user `BeforeWorkerStart` listeners, covered by its existing test. Preserve per-process pool resets, shared table setup, cache-policy finalization and worker-local validation where they depend on initialized resources or worker bindings. Update the obsolete rationale in Auth, Cache and Sanctum. Do not move code that opens resources into the pre-fork parent.
4. **Keep config-write tracking for PHPStan alone.** The resolver combines the provider source with direct writes observed after config loading. Executed merge closures and their values are unnecessary. Register the existing Foundation `ConfigMutationTracker` explicitly during analysis. For apps, bind it before kernel bootstrap. For packages, bind it in the resolving callback passed by PHPStan's `ApplicationResolver` to Testbench. At the end of Foundation's initial config load, attach the observer only for that explicit binding. This point includes Testbench's subsequent testing-connection writes and excludes the initial config-file loads. Use a deduplicated set of direct keys and an internal key accessor in place of PHPStan's private-property read. Detach the observer when analysis bootstrap finishes. Ordinary serving, CLI and queue processes should retain no mutation history.

   Preserve protected `ServiceProvider::configureUsing()`, its config-cache guard, normal package merges, replacement semantics and callback ordering. Execute the callback once. With tracking active, suppress recording around the callback and restore it in `finally`, including nested calls. The analyzer already distinguishes merges and inspects callback writes. Recording a whole merged subtree as a direct write would lose source precision. Simplify the deprecation logger's replay closure to the actual one-time setup, preserving explicit channels and lazy null-channel creation. Keep `Repository::replaceItems()` where exact restoration is needed by test helpers, including absent keys. Retain its internal status. Keep this work off request and config-read paths. Attach it at the end of Foundation configuration loading.

   ```php
   if ($app->bound(ConfigMutationTracker::class)) {
       $app->make(ConfigMutationTracker::class)->observe($config);
   }
   ```

   Use `bound()` because a bare `make()` would auto-singleton even an unregistered tracker.
5. **Keep maintenance mode's best-effort recycle.** Rename Foundation's Hypervel-specific `ReloadsWorkers::reloadWorkers()` to `RecyclesWorkers::recycleWorkers()`, including `down`, `up` and their test overrides. Delegate the trait's operation to the dedicated command via `callSilently(ServerRecycleWorkersCommand::class)`. Foundation already requires Server. Ignore unsuccessful delivery for these maintenance commands as today. This also avoids their current permissive PID cast signalling a numeric prefix in a malformed file. Keep their committed-state and follow-up exception handling.

   Clear `WorkerCachedMaintenanceMode`'s in-memory snapshot on worker startup before serving traffic. Normal middleware first reads it in the worker, but a provider can call `isDownForMaintenance()` before fork. With automatic refresh disabled, a replacement then inherits the stale answer indefinitely. Verified with the file driver across a fork. Reset only the cached snapshot and timestamp via the existing `flushCache()` and leave the underlying maintenance state intact. Test the pre-warmed case against changed driver state through the worker-start event and keep steady-state request reads unchanged.

6. **Update live guidance and consumers.** Use the server guide as the canonical explanation of this command.

   ```sh
   php artisan server:recycle-workers
   ```

   Explain what is replaced, custom process lifetime, the drain allowance and the difference between PROCESS and BASE connections. Replace the config exception list and invalid-refresh loop with one restart instruction. Update the lifecycle table and links in deployment, signals and server processes. Explain config-cache deployment and maintenance recycling in `configuration.md`, computed boot values and cached config in `providers.md`, and inherited exporter/instrumentation settings and computed defaults in `opentelemetry.md`. In JWT/Passport commands and docs, keep the precise key-rotation restart instruction for every long-running process that uses those keys. Correct Doctor's repair advice and audit AI skill and Inertia asset-version cache guidance according to when those caches are populated. Put the Octane deployment difference in the Laravel porting guide. Remove the resolved server-reload investigation from `docs/todo.md`. Search active code, tests, skeletons, docs and consumers for literal command names, anchors, replay APIs and descriptions of worker config reload. Preserve historical plans and valid uses of “reload” in other services.
