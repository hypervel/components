# Guzzle forks: hypervel/guzzle and hypervel/guzzle-promises

**Status:** complete. Both forks are released (`hypervel/guzzle-promises 3.0.2.2`, `hypervel/guzzle 8.2.0.1`), and the components integration and focused comparison are verified. The broader performance study is tracked in `docs/todo.md`.
Replace Hypervel's Guzzle AOP instrumentation (three ownership aspects, the Sentry and Telescope `GuzzleHttpClientAspect`s and PHPUnit proxy preparation) with two maintained forks that carry coroutine ownership and global middleware natively, and drop Guzzle 7 / promises 2 / PSR-7 2 support. Generic AOP machinery (proxy generation, dispatch, caching, loaded-class validation, `InteractsWithAop`, `aspects()`) stays.

This replaces the AOP design in [2026-10-09-guzzle-coroutine-ownership.md](2026-10-09-guzzle-coroutine-ownership.md).

## 0. Requirements

Upstream API compatibility is a hard requirement for both forks. Composer installs them in place of upstream for third-party packages and SDKs, so existing calls and implementations must keep working unchanged: do not break existing public contracts (names, signatures, parameters, interfaces others implement) or add required methods to existing interfaces, and keep new APIs backward compatible. Each fork's `AGENTS.md` and README state this prominently.

No Laravel API changes. Removed Hypervel-only surfaces: `Hypervel\Http\Exceptions\CoroutineOwnershipException`, the `no_sentry_aspect` option (becomes `sentry_enabled`), `ClientRequestWatcher::recordRequest(ProceedingJoinPoint)`, `HandlerFactory::DEFAULT_MAX_IDLE_HANDLES`.

## 2. What hypervel/guzzle-promises provides

The fork's README [Hypervel Fork](https://github.com/hypervel/guzzle-promises/blob/3.0/README.md#hypervel-fork) section and its `docs/promise-api.md` sections [Coroutine Ownership](https://github.com/hypervel/guzzle-promises/blob/3.0/docs/promise-api.md#coroutine-ownership) and [Task Queue](https://github.com/hypervel/guzzle-promises/blob/3.0/docs/promise-api.md#task-queue) document these changes.

- **Promise ownership.** A pending `Promise` belongs to the coroutine that created it (`-1` outside coroutines). The owner is recorded in the constructor, so promises created before Hypervel registers anything are checked too. While a promise is pending, another coroutine's `then()`, `otherwise()`, `wait()`, `cancel()`, `resolve()` or `reject()` throws a plain `\LogicException` (`Coroutine 5 cannot call then() on an unfinished promise owned by coroutine 3. …`) and leaves the promise unchanged. This replaces `PromiseConstructionAspect`, `PromiseOperationAspect` and `CoroutineOwnership`'s promise maps.
  - Resolving or rejecting with another coroutine's pending `Promise` or `Coroutine` is refused the same way, before any change.
  - A promise resolved with a pending promise stays owned until that value settles, including a pending third-party `PromiseInterface` at the end of the chain. Once a promise and everything it was resolved with have settled, any coroutine may chain on or wait for it.
  - `Coroutine::cancel()` checks the owner of its result promise before cancelling its current promise, which may come from another library and carries no owner.
  - Settling a promise with a value whose resolved chain leads back to it, such as `$b->resolve($a)` after `$a->resolve($b)`, throws a `\LogicException`.
- **Scoped task queue.** `GuzzleHttp\Promise\ScopedTaskQueueInterface` extends `TaskQueueInterface` with `track(PromiseInterface $promise): void`. A scoped queue runs tasks per execution scope, such as a coroutine, and cancels pending work tracked in a scope when that scope ends. `Utils::queue()` is unchanged, and the stock `TaskQueue` does not implement the interface. Coroutine applications need a separate queue for each coroutine, because promise callbacks settle promises in the coroutine that drains the queue (§5.1).
- **Tests.** The non-proxy cases of components' `tests/Http/Client/Guzzle/PromiseOwnershipTest.php` live in the fork's `tests/PromiseTest.php` and `tests/CoroutineTest.php`, and fork CI runs upstream's complete suite (§5.6).

## 3. What hypervel/guzzle provides

The fork's README [Hypervel Fork](https://github.com/hypervel/guzzle/blob/8.2/README.md#hypervel-fork) section, its `docs/handlers.md` sections [Coroutine Ownership](https://github.com/hypervel/guzzle/blob/8.2/docs/handlers.md#coroutine-ownership) and [Idle cURL Handles](https://github.com/hypervel/guzzle/blob/8.2/docs/handlers.md#idle-curl-handles), and its `docs/middleware.md` section [Global Middleware](https://github.com/hypervel/guzzle/blob/8.2/docs/middleware.md#global-middleware) document these changes. Both forks `replace` their upstream package (`self.version`) and require PHP `^8.4` and `ext-swoole`, so packages and SDKs with compatible `guzzlehttp/guzzle` or `guzzlehttp/promises` version requirements get the forks without code changes (§4).

- **Multi-handler ownership.** A `CurlMultiHandler` with pending work belongs to the coroutine driving it; another coroutine may claim it only when it is idle and no handler call is running. Until then, another coroutine's `__invoke()`, `tick()`, `execute()` or `close()`, and its waits on or cancellations of the handler's transfers, throw a `\LogicException` (`Coroutine 5 cannot call tick() on a cURL multi handler with work owned by coroutine 3. …`) without changing the handler. A queued tick from a coroutine that no longer owns the handler does nothing. This replaces `TransportOwnershipAspect`, `TransportState` and the transport half of `CoroutineOwnership`.
  - Only `CurlMultiHandler` has an owner. It handles asynchronous requests without `stream`, and synchronous ones too on clients with connection caps, which components' `HandlerFactory` rejects (§5.1). `CurlHandler` and `StreamHandler` return settled promises.
- **Scoped tracking.** After a successful `addRequest()`, `CurlMultiHandler::__invoke()` passes the pending transfer to `Utils::queue()->track()` when the queue implements `ScopedTaskQueueInterface` (§5.1). A failed add is not tracked.
- **Global middleware.** `Client::pushGlobalMiddleware(callable $middleware, string $name): void` and `Client::removeGlobalMiddleware(string $name): void` manage process-wide middleware that wraps the transfers of every client, including clients inside SDKs. Sentry and Telescope use it to instrument Guzzle without AOP (§5.3, §5.4).
  - It has the same form as handler stack middleware. Register it once at startup.
  - It wraps each transfer outside the client's handler stack. It receives the request after `base_uri` resolution but before request options such as `headers`, `query`, `body` and `json` are applied, and the request options merged with the client's defaults, with null values removed.
  - The first middleware pushed runs outermost, as with `HandlerStack`. Pushing a registered name again replaces that middleware and moves it innermost.
  - It must return a promise. The next handler throws synchronously when the client cannot apply the request options; other exceptions thrown by middleware reject the returned promise.
  - The chain is composed for each transfer, so the middleware is called with the next handler per transfer; keep state shared across transfers outside that call. Caching the chain on the client would hold the client in a reference cycle and delay freeing its native handles.
  - Cost: about 60 ns per transfer with nothing registered and under 1 µs with two pass-through middleware, against roughly 6 µs for a client transfer through a trivial handler.
- **Idle cURL handles.** `CurlHandler`'s default `max_idle_handles` is 256 instead of 3; `CurlMultiHandler` keeps 50, and explicit values are honored. Coroutines overlap synchronous requests on one handler, and each easy handle has its own connection cache, so with 3 most concurrent requests would reconnect. The fork's literal is the only definition; components drops its constant (§5.1).
- **Carried upstream PRs:**
  - [guzzle/guzzle#3934](https://github.com/guzzle/guzzle/pull/3934) keeps `StreamHandler` deadlines local to each request.
  - [guzzle/guzzle#3935](https://github.com/guzzle/guzzle/pull/3935) adds `max_idle_handles` for `Utils::chooseHandler()`, `CurlHandler`, `CurlMultiHandler` and `Client`.
  - [guzzle/guzzle#3936](https://github.com/guzzle/guzzle/pull/3936) returns available bytes from filtered streamed responses instead of waiting for a full buffer.
  - [guzzle/guzzle#3937](https://github.com/guzzle/guzzle/pull/3937) reads `StreamHandler` response headers from the opened stream, which also fixes the stream handler under Swoole on PHP 8.4 and newer.
- **Tests.** The pure handler cases of components' `TransportOwnershipTest` live in the fork's `tests/Handler/CurlMultiHandlerTest.php`, and fork CI runs upstream's complete suite (§5.6).

```php
/**
 * Retain a pending transfer in its owner's context until it settles.
 */
public function track(PromiseInterface $transfer): void
{
    $identifier = spl_object_id($transfer);
    $this->transfers[$identifier] = $transfer;
    $release = function () use ($identifier): void {
        unset($this->transfers[$identifier]);
    };

    $transfer->then($release, $release);
}
```
