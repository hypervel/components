## Design decisions

- Port Larastan's architecture, file organization, naming, algorithms and applicable tests; track its upstream. Use `cp`, read the complete copy, then edit, one file at a time in alphabetical order. Use `mv` for existing Hypervel extensions. Preserve upstream member order and comments (unless incorrect). Fix inherited defects at their owning boundary.
- Boot the actual application; use Hypervel Testbench for packages. Retain runtime discovery of container bindings, macros, facade roots, authentication configuration and console definitions. Do not build a second static service-container simulator or require an alternative no-boot mode.
- Retain the upstream `extension.neon`, parameter schemas, PHPStan DI attributes and applicable rule switches. Select stricter Hypervel defaults. Keep settings for retained features, including paths and scanning/cache options; omit settings only when their feature is omitted. Do not implement anti-override mechanisms, non-ignorable policy errors, multiple strictness profiles, or a custom configuration language.
- Register `extension.neon` in `extra.phpstan.includes`. Document explicit inclusion and optional discovery through `phpstan/extension-installer`; installing the analyzer alone does not install or authorize that Composer plugin.
- Include maintained deprecation reporting through a required `phpstan/phpstan-deprecation-rules` dependency. Use normal `@deprecated Use X instead.` metadata for future Hypervel deprecations; do not build duplicate deprecation rules. Reporting covers known deprecated APIs from dependencies and PHP as well as Hypervel, subject to upstream metadata and deprecated-scope behavior. PHPStan's restricted-usage rules look members up on the plain class, so deprecated members reached through generic proxies (higher-order collection, `when()`, `Optional`, tap) are not reported; proxy reflections still carry the target's deprecation metadata, the docs state the limit, and no duplicate rule or dependency patch is added.
- The public configuration catalog below is the source of truth for defaults. Preserve PHPStan's own level, paths, parallelism, baseline and suppression settings. PHPStan already defaults unmatched-ignore reporting to true; remove the three consumer false overrides after auditing their ignores rather than redundantly setting that default in the extension. Stronger defaults do not change the meaning of retained options.
- Package-owned diagnostics use stable `hypervel.*` identifiers, state the concrete problem and give the replacement. Rename Larastan-owned identifiers (`larastan.*` and `rules.modelAppends`) only; preserve PHPStan-owned identifiers emitted by reused offset/argument checks, such as `offsetAccess.notFound`. Keep ordinary suppressions for legitimate exceptions and analyzer limitations. New rule switches follow Larastan's boolean parameter/conditional-registration convention; do not add detailed tuning without a real requirement.
- Use PHPStan rules, type/reflection extensions, restricted-usage extensions and collectors for their intended jobs. Collectors can supply cross-file diagnostic facts after analysis; they cannot feed same-run type inference. Share an existing helper where needed, not a parallel inference engine.
- Runtime work is confined to genuine source typing/correctness fixes exposed by this port and changes needed to support the analyzer correctly. Configurable authoring-policy diagnostics can recommend modern APIs while legacy APIs remain supported. The separate legacy-removal todo is not permission to remove runtime APIs in this port; see the legacy-policy section.
- Shared component release versions apply. New mandatory defaults belong in a `0.x` minor release; false-positive corrections can ship in patches. Do not introduce an independent analyzer release train.

Skip a residual entry that is base-only and identical to its initial value; added or changed residual values still apply. This preserves `loadConfigurationFile()`'s returned residual-value contract, not an override's direct repository write to a base-only key, which the old loop reset. Test the nested case and one override adding and changing residual values, in both copies. Then remove `ConfigParser::composeConfig()`'s special case that models the overwrite.
- **Merging.** Follow the runtime: `array_merge` at the top level and at each mergeable option (string keys: the higher source wins; integer keys: appended and renumbered), and `replaceConfigRecursivelyFrom` replacing by key at every depth. A higher array with unknown keys (an unsealed `@return` shape) may replace any lower entry it does not list, so in both merges those entries become unknown. A definite package merge reads its target's presence as trinary: a definitely absent key takes the package's values, while a key that may be present (optional, or unlisted in an open array, whose missing intermediates stay open) is unknown, because the application's values win only where it set them. Read mergeable options once per instance and key from the real `mergeableOptions()` of a `LoadConfiguration` and of the booted provider; do not copy their tables.
- **Provider merges.** Find `mergeConfigFrom()`/`replaceConfigRecursivelyFrom()` calls from the cached AST of loaded providers' class hierarchies and traits, excluding `ServiceProvider`. PHPStan scopes do not fold `__DIR__` (`usePathConstantsAsConstantString` is off, and must stay a consumer setting), so resolve arguments with php-parser's `ConstExprEvaluator`: the source file's `__DIR__`/`__FILE__`, global `dirname()` with constant arguments (bound by name; unpacking is not constant), class constants, and the current string value of a `self::`/`static::` property that is provider boot metadata (Sentry's documented boot-only `$abstract`). This is metadata argument resolution, not expression execution or runtime value typing. A merge is definite when its arguments resolve and it lies on the straight-line path from the effective (most-derived) `register()`: top-level `parent::register()` and `$this->helper()` statements followed under an active recursion guard (a helper called twice runs twice), with no earlier `return` outside nested closures. An earlier `throw` cannot have run in a booted application. Boot-time merges, merges of overlapping keys by different providers and every other resolved call are candidates; resolving arguments does not prove execution. Enumerate the registered providers once (`getProviders(ServiceProvider::class)`). Creating a callable runs nothing: `$this->helper(...)` is not followed, and a callable created from a merge method is an unresolvable merge. A resolved file is a package config file even when its key is not.
- **Mutations widen the composed type.** Direct writes come from the keys of the array entries `ConfigMutationTracker` records after LoadConfiguration attaches it, read once through the analysis-only `(fn () => ...)->call()` pattern. These cover Testbench's testing connection, user model and database/queue rewrites and provider `set()`/`push()`/`prepend()` calls. Never read the recorded values or run or inspect the recorded closures. `configureUsing()` writes are not recorded, so scan closure callbacks in provider hierarchies, from the cached AST, for writes through a recognized repository receiver (`set()`, `push()`, `prepend()`, offset assignment or unset). Recognized receivers, by resolved function and class identity: the callback's parameter, a method parameter typed as the repository contract or concrete, `config()`, global `app()`/`resolve()` with `'config'` or the repository class, `$this->app->make()`/`get()` with the same ids, plus `config([...])` and Config facade writes. The container has no `ArrayAccess`, so there is no `$this->app['config']` form. Known reads (`get()`, `has()`, the typed getters, `collection()`, `all()`, `getMany()`, offset reads) are not effects. Passing, reassigning, capturing or returning the callback parameter, calling any other method on it, or a non-closure callback is an unlocalizable write; an unrelated `app()`/`$this->app` use is not a write. Bind arguments by their real parameter names (`key`, `offset`, `abstract`, `name`, `id`) with `getArg()`, never by position, since the provider AST is not PHPStan's reordered call; an unpacked key is unlocalizable. Creating a callable from `config(...)` or a repository method writes nothing; inside a callback it is an unlocalizable write, since its later calls cannot be followed, unless it comes from a read-only method.
  - The same pass records constant keys of direct writes through recognized receivers anywhere in the provider class-likes, covering branches the CLI boot did not run. The tracker stays authoritative for executed writes, so unrecognized flows (locals, helpers, other services) are not treated as writes. This is a documented best-effort boundary: an unexecuted write through an unrecognized flow is not found.
  - Resolve a write key fully first. Otherwise bound it by its constant leading part (concatenation or interpolation) up to the last proven dot boundary: `'filesystems.disks.disk_' . $name` writes `filesystems.disks`, `'filesystems.disks' . $suffix` writes `filesystems`. Without a complete segment it is an unlocalizable write. One helper serves callbacks and direct writes.
  - A replacement at P makes lookups at or below P unknown and widens P to optional `mixed` in its ancestors.
  - A candidate merge at K unseals K and its string-keyed mergeable options, keeping their known fields. Numeric merge levels and non-array ancestors, which `Arr::set()` replaces, are replacements.
  - An unresolvable merge target or an unlocalizable write makes every lookup unknown.
  - Mergeable options are named-entry registries that framework code extends at runtime, so they stay unsealed. An unsealed tail covers additions, not replacements: HandleExceptions fills a falsy `deprecations` or `null` log channel inside a recorded closure, so a registry entry whose known value may be falsy is unknown. Other known entries keep their exact types.
- **Lookup.** Walk offsets with PHPStan presence (`hasOffsetValueType()`). Present gives the value alone, so a default cannot hide an incompatible value. Maybe gives the value or the default. Absent gives the default, or null without one. Unknown keeps the declaration. Evaluate only `Closure` defaults to their return, as `value()` does: the default itself or its union alternatives, never a Closure it holds. Cover `config()`, the Config facade's `get()`, typed getters and `collection()`, and the repository contract (which also covers the concrete repository), only for methods the contract, the concrete repository or the facade declares. A custom implementation or override keeps its declared type, and the rules skip it too. On a repository receiver this includes what a getter delegates to: the typed getters read through `get()` and `collection()` through `array()`. Facade calls forward to the bound repository, so only the called facade method is checked. Typed getters intersect their native type with the result, and an unknown `collection()` keeps its declaration. During recursive lookups an in-progress discovery is unknown and is not cached; publish derived caches only after discovery completes.

Retain `configDirectories`, `viewDirectories`, `translationDirectories`, migration/schema paths and associated upstream settings for retained features. Prefer boot-discovered paths by default; document exactly whether an explicit setting replaces or supplements discovery. Larastan's configured migration/schema paths replace its fallback paths; preserve that contract unless a separately justified adaptation changes it. A non-empty `viewDirectories` likewise replaces the booted finder's paths and namespace hints, for the unused-view rule only; the missing-translation rule always scans the finder's paths, as upstream does. By default the unused-view rule names root views from the finder's paths and scans namespace hint directories for usages only: framework and package views such as `pagination::tailwind` are rendered by names no literal call shows.

### Model schemas

Port migration aggregation and `MigrationCache`, covering MySQL, MariaDB, PostgreSQL and SQLite without a live database connection. Dumps and literal migration SQL are parsed by `hypervel/schema-parser` ([docs](../../src/docs/schema-parser.md)), with the parser chosen by the connection's driver. Dialect parsing belongs to that package; the analyzer maps its results to PHP types. Real defects this work exposes in it are fixed in that package on this branch, through the normal second-opinion and review workflow. Package schemas and schemas owned by other services can be supplied through the retained path settings. Fixtures are real `schema:dump` output for each driver, generated from the fixture app's migrations.

Default migration discovery follows `migrate`: the booted migrator's `paths()` (providers' `loadMigrationsFrom()`, which may name files), then `database_path('migrations')`, as `BaseCommand::getMigrationPaths()` orders them, read through `Migrator::getMigrationFiles()`: top-level `*_*.php` files, a later path's file replacing an earlier one with the same migration name (a published migration replaces its package's), applied in name order. A non-empty `databaseMigrationsPath` replaces both and keeps upstream's recursive `.php` scan, ordered by file name; `disableMigrationScan` still applies. One resolved list feeds discovery and dependency tracking: named files as file dependencies, directories with their discovery pattern.

Runtime fix: `DumpCommand` resolves its connection through `Migrator::resolveMigrationConnectionName()`, as `MigrateCommand::loadSchemaState()` does, so `schema:dump` runs on and names its file after the routed migration connection (the shipped `pgsql-pooled` routes to `pgsql`). Test the routed connection and default filename with default and explicit selection.

Runtime fix: SQLite fetches a JSON number from a `json`/`jsonb` column as an int or float, which the strict-typed `json_decode()` rejected. `Casts\Json::decode()` returns such a number unchanged after the custom-decoder branch (which still receives the raw value), so every JSON cast reading through it works; `HasAttributes::fromJson()` and `jsonIsEquivalent()` accept `string|int|float|null`, as Laravel's untyped methods do. Covered by an SQLite hydrate, read and dirty-check regression and decoder tests.

- **Identity.**
  - Facts belong to an owner: `Migrator::resolveMigrationConnectionName()` of the connection's `ConnectionName::parse()->base`, so a pooled model and its migration connection share facts. A config error the method rejects gives unknown identity.
  - Facts are keyed by owner, schema (or none) and physical name: the requesting connection's `prefix` applied once to a logical name's final segment, as `Grammar::wrapTable()` does. Dump and raw-SQL names are already physical.
  - Each side uses its own connection's effective config. Model lookups and fetched types use the model connection's. A migration statement (Blueprint or raw) uses its explicit `Schema::connection()`/`DB::connection()` name, which is not redirected, else the routed migration connection (`Migrator::runMethod()`).
  - Connection names are evaluated, never executed: string and null literals (empty selects the default), the migration's `$connection` property, a `getConnection()` override that returns one expression, `config('key'[, default])`, `config()->get()`/`string()` and the `Config` facade's with a literal key, and `??` of these, reading only the side that runs. The migration's own `getConnection()` and `$connection` are read from its class, inherited ones only when `Migration` declares them; one a used trait declares (nested traits included), a trait alias names or an unknown trait could supply is unknown, as for methods (below). A `$connection` that a method other than `down()` assigns (also by reference or compound assignment), or that a promoted constructor parameter sets, in the migration or in code it inherits or uses from traits below `Migration` (an unreadable class or method counts as a write), is unknown; constructors are never run and assigned values never interpreted; an explicit literal selection stays known. Config reads use the booted repository and keep a present null distinct from a missing key; `string()` and a `string` return type are known only for a string. Anything else is unknown, as is a kept first-class selector callable. Passport's and Telescope's published migrations are the reference cases.
  - Effective config is deterministic: `parseConfig()`, then per-record `configForRead()`/`configForWrite()` as `DatabasePool::roleEndpoints()` does, never the `Arr::random()` selection. A `::read` name uses its read records; a base name uses read and write records, because reads can use either PDO. A `DB::extend()` connection uses its parsed config and reads `mixed`. Driver, prefix, `database`, schema/search path and username must agree across records, otherwise that connection's lookups are unknown; fetched types are the union over the distinct option sets.
  - A dump is `{connection}-schema.{sql,dump}`, for a booted `database.connections` key, in a `squashedMigrationsPath` directory. `.dump` wins over `.sql`, as in `MigrateCommand::schemaPath()`.
  - Any other name keeps unknown identity: document the naming requirement and never assume the default connection.
  - Index tables, views, and PostgreSQL enums and domains by owner, schema (or none) and name, keeping unqualified definitions distinct. Never use the package's unqualified lookups, which throw on ambiguity.
  - MySQL/MariaDB: an unqualified definition belongs to the connection's configured `database` (`schema:dump` writes no `USE`, and unqualified DDL targets the current database). SQLite definitions carry `main` or the attached database's name.
  - PostgreSQL tables: an unqualified model table resolves through `PostgresBuilder::getCurrentSchemaListing()`'s precedence (`search_path`, then `schema`, then `public`; `$user` is the configured username), read from config only, taking the first schema with a qualified definition. An unqualified definition (from Blueprint or literal migration SQL) records the defining connection's resolved path and matches only a model connection with the same path, and only when no qualified candidate exists, because unqualified creation lands in the first existing path schema. An unqualified definition beside a qualified candidate, or a qualified model table with only an unqualified definition of that name, is ambiguous.
  - PostgreSQL types: an unqualified type name resolves through the same precedence, with `pg_catalog` searched first unless the configured path names it explicitly, as PostgreSQL does. A name that resolves to no known built-in or dump-defined type reads `mixed`. A domain's unqualified base that names a user type reads `mixed` unless the effective path is `pg_catalog` then one schema, because a type of that name created later in an earlier path schema would shadow the one the domain was created with; a domain chain that revisits a domain (only after failing migrations that drop without `CASCADE` and recreate) reads `mixed`. A type fact can be uncertain (`null`: its definition or presence is unknown); reaching one reads `mixed` without searching later schemas. Domains resolve through the type facts, never through the base the parser embeds in a column, and an array (including an array of a domain) reads as its text representation first.
- **Completeness.**
  - A connection is incomplete when its dump cannot be read, throws `ParseException` (the PostgreSQL parser rejects `PGDMP` custom archives), has schema-level issues, or its driver has no parser. A dump that is not interpreted (unreadable, unparsable or without a parser) also makes the owner's other dump facts unknown, since it may define any relation they define. Schema-level issues also make that input's tables incomplete and its types uncertain, as for raw SQL. A relation that two dumps of one owner both define is unknown; a type they define differently is uncertain, and a later dump does not restore it. An owner with no schema source (no dump and no interpreted statement) is unknown, not proven empty.
  - A table is incomplete when it has issues, is a view (no column facts), is ambiguous, or is affected by the migration-side cases below.
  - Known columns keep their types and casts unless a migration-side case makes them uncertain. An incomplete dump table that the same dump alters (`Impact::$relations`) is unknown: the parser could not apply that alteration, so a kept column may be gone or retyped. An unknown column on an incomplete table or connection gets no missing-column claim, while complete tables still report one.
  - With no established facts for the model's table, an undeclared name is maybe an attribute: the property extension defers to a declared relation (or its `_count`; a relation method named exactly like a count wins over the count) before assuming one. A model runtime reflection cannot instantiate has no established facts either. Neither has an abstract model (including `Model` and template bounds), but the property extension does not claim its names: a model trait's `@mixin Model` (Scout's `Searchable`) would then give every model every property. `ModelPropertyHelper::acceptsPropertyName()` instead accepts any name for an abstract model, evaluating union alternatives separately (intersections whole) and keeping the concrete alternatives' results; `GenericModelPropertyType::accepts()`/`isSuperTypeOf()` and dynamic `where{Column}` use it. Only a complete known schema rejects a column. A known cast key is an attribute without a column, as `HasAttributes::hasAttribute()` accepts it; undetermined method casts do not make every name one.
- **Uninterpretable migrations.** A construct the aggregator cannot interpret makes the facts it could affect unknown, types included: an unknown Blueprint method (macros), a helper or other escape of `$table`, a non-constant column name in a `change()`, loops and other control flow make the table unknown; an added column with a non-constant name makes the table incomplete, keeping its known columns; an unknown table argument makes the owner unknown; an unknown connection, or a migration file that does not parse (upstream skipped it), makes every owner unknown. Do not build a PHP interpreter.
  - Facts come only from code applied as executed: `up()`, the methods it calls on `$this`, `self`, `static` or `parent` (`$this::` as `static::`; after their arguments, which are searched), Blueprint callbacks (including `after()`), `withoutForeignKeyConstraints()` and `whenTable(Doesnt)Has(Column|Index)()` (the column guard is decided like `hasColumn()`; index guards join both outcomes). Other code, including closures and helpers in nested positions, is searched for Schema and DB calls, which only make their targets unknown. A first-class callable created as a statement runs nothing; a kept one (assigned or passed) makes its targets unknown, since it can run later with any arguments. A callable array naming one of those methods (`[$this, 'm']`, or `self::class`, `static::class` or `parent::class` first) is searched the same way, as the equivalent call with the same dispatch. A dynamic method name on those receivers, including a callable array's non-literal name, makes every owner unknown. Callable variables and class-string callables are not followed. A dynamic method name on a recognized Schema receiver (the facade, a selector or a builder variable) makes that connection unknown (every owner when the connection is unknown). Code that cannot be read (an unreadable or dynamically named method, an unparsable migration file) and a dynamic Schema method also make the morph key type unknown; an unknown connection alone does not. Dynamic names on `DB` calls stay within the query-chain boundary below. Arguments of recognized Blueprint and Schema calls are read only for the supported values described here, not searched for other schema changes; statements in other contexts are searched as above.
  - `up()` and those methods may be inherited from a parent migration or a trait. They are found through reflection, parsed from the declaring file with the migrations parser and dispatched as PHP does: `$this`/`static::` on the migration, except that `$this` reaches a private method of the class declaring the calling body first (PHP binds private calls to the calling scope); `self::` on that class, `parent::` on its parent. The files of the migration's parents and traits below `Migration` (`SourceFiles::forClass()`, recorded once per migration) are sources of every fact, because an edit to any of them can change which method runs, or whether inherited code sets the connection, while the selected body's file stays unchanged. Recursion is detected per declaration, so a method calling its parent's same-named method runs both. `Migration`'s own methods change no schema. A method whose body cannot be read (an unknown class, an unparsable file, a trait use with conflict resolution or aliases, including an alias that supplies the called name) makes every owner unknown; aliases are not resolved. Bounded method lookup only: no call graph across other objects and no argument-value interpretation.
  - Assigning a Blueprint's `engine`, `charset` or `collation` property sets a table option and keeps the table's facts; the assigned value is searched like any expression. Other Blueprint property writes escape.
  - `removeColumn()` only cancels the definitions its Blueprint queued, so its column becomes uncertain (never a drop). A non-literal `unsigned` makes only that MySQL column's type unknown.
  - `addColumn()`'s literal parameter bag applies over its type and name, as `Blueprint::addColumn()` merges it, and later fluent modifiers win; a non-literal bag makes the table unknown. A `type()` modifier replaces the column's type (a non-literal one makes it unknown) and drops enum allowed values. On a `foreignId*` column, `constrained()`/`references()` return a `ForeignKeyDefinition`, so only the modifiers inside the innermost such call apply to the column; on any other column they are Fluent attributes and the chain stays the column's. `fill()`, `set()`, `offsetSet()` or `offsetUnset()` in the column's chain can set any attribute, including its type and nullability, so it makes the table unknown; so do calls chained after `removeColumn()`, which returns the Blueprint.
  - Rename, drop and `change()` targets match column names as the driver does: ignoring case on MySQL/MariaDB/SQLite (keeping the stored spelling; an ambiguous match makes the table unknown), exactly on PostgreSQL. A `change()` naming a stored column in another case makes the table incomplete, since the resulting spelling depends on the server.
  - Builders in local variables, without tracking data flow: per applied method or closure (cached per function; an arrow function shares its parent's), a variable holds a builder when every write is an assignment statement of a Schema selector (`Schema::connection()`, `DB::getSchemaBuilder()`, `DB::connection()->getSchemaBuilder()`), all selecting one connection, and every other use, nested functions included, calls a method on it. Its calls are followed like `Schema::` calls. Any other variable assigned a Schema or DB selector escapes: the selector and every later use of the variable make the selected connection unknown (every owner when unknown). A Schema selector not consumed by a recognized call or builder variable, and a `DB::connection()` that is not a method receiver, also escape. Query chains on a DB connection (`DB::connection()->table()->update()`) keep facts; this is the supported query-chain boundary, not proof that no method call changes the schema. A DB connection stored in a variable escapes even when its later calls only update rows: a known precision loss, not an unsupported pattern. Aliases of aliases, builders reached through properties, and statements on connections reached other ways (`$this->db`, `app('db')`) are not followed; the docs state these boundaries and keep them distinct from followed Schema-builder variables.
  - PostgreSQL inheritance and partition descendants change with their parent (Blueprint DDL has no `ONLY`; dropping a partitioned table drops its partitions). Every Blueprint alter, drop or rename and every raw-SQL impact relation also makes the known descendants unknown, found through the parsed `parents`/`partitionOf` links. Regressions: a dump with a parent and child followed by a raw `ALTER COLUMN TYPE` on the parent, and a Blueprint `Schema::table()` on the parent.
  - `if`/`elseif`/`else`/`switch`: apply each outcome, including the fallthrough, to cloned state and merge at each boundary. A case body ends at its first top-level `break`; a case that can leave the switch elsewhere (a nested `break`/`continue` whose level passes the loops and switches between it and the case; function and class bodies excluded) makes the switch's affected facts unknown, as a loop does. A column or table absent from any outcome becomes uncertain (`mixed`, no claim; a missing attribute reads null). An identical `ColumnType` in every outcome keeps its type with nullability ORed; differing types read `mixed`. A user type that one outcome lacks or defines differently is uncertain.
  - `Schema::hasTable()`/`hasColumn()` guards (also through a selector or builder variable, negated or compared with `true`/`false`) are decided only from established facts of a known owner and complete table, ignoring letter case as the framework can; otherwise the condition is unknown. An early `return` ends its outcome for the rest of that body. Each body keeps at most a continuing and a merged returned state.
  - Blueprint commands run once the callback returns, while the aggregator applies them at once. A guard inside the callback on the callback's own table (same owner, and the same physical name or a current lookup giving its key) therefore reads a copy saved when the callback starts: the resolved table for `table()`, the previous table at the key or none for `create()`. The copy is used only while the current table exists and is complete; otherwise (an immediate change such as a nested `Schema::table()`, or a queued drop or rename the facts already apply) the guard is unknown. With no saved table, `hasTable()` is false only under the absent rule (complete owner, no case variant besides the callback's key). An ambiguous lookup stays unknown, and the saved and current tables' sources are recorded.
- **Raw migration SQL** (`DB::statement()`/`unprepared()`, directly or through `DB::connection()` or `Schema::getConnection()`). Each parse starts empty, so its snapshot does not describe changes to the accumulated schema; the parser's `Schema::$impact` summary does. Each relation it lists (altered, dropped or renamed, including both rename names, whether or not the input also defines it) becomes unknown, and `unknown` makes the owner's earlier facts unknown and skips the input's definitions. Each type in its `types` list (an enum label change, a non-renaming `ALTER DOMAIN`, or a drop; renames, schema moves, other type changes and `CASCADE` set `unknown`) becomes uncertain before the input's definitions apply: a qualified name marks its own key, recorded or not, which stops any search through its schema (an unqualified definition was created in a path schema, so it stays known); an unqualified name marks the existing unqualified and configured-path keys. Index and comment statements keep facts. Created definitions add facts; one for a relation that exists or may exist (an incomplete owner) makes only that relation unknown, since the snapshot does not distinguish `IF NOT EXISTS`. Schema-level issues make the input's tables incomplete and its types uncertain. `ensureExtensionExists()` is classified like raw `CREATE EXTENSION`. Explicit casts and accessors stay authoritative.
  - MySQL/MariaDB identities stay exact, but each mutation also makes known relations whose database and table names differ only in letter case unknown, because some servers fold them. Lookups are not case-folded.
  - Inference uses the configured connection identity and does not track session state carried across separate raw calls (`USE`, `SET search_path`). This is an analysis limitation: the Static Analysis docs state it and recommend a configured connection for another database or schema, and a short WHY comment at the impact handling records it.
  - Regressions: drop-and-recreate versus `CREATE TABLE IF NOT EXISTS` after a Blueprint table, a raw drop or rename leaving no missing-column claim, a raw index preserving earlier facts, a MySQL raw `ALTER TABLE Users` after a Blueprint `users`, `removeColumn()` after `->change()` keeping the column, `whenTableHasColumn()` with a decided and an unknown guard, and `DB::transaction(fn () => Schema::create(...))` leaving no missing-table claim.
- **Diagnostics.**
  - A `PropertyFetch` collector (nullsafe fetches included) records the unusable-dump facts (path, line, message) of the model's connection when a model's undeclared property is read. It does not track whether the lookup reached the schema (an `@property` tag, for example), since that would need order-dependent state in the helper. The data is serializable and loaded lazily.
  - A `CollectedDataNode` rule (`hypervel.schemaDump`) reports each unusable dump (unreadable or a `ParseException`) once, at the dump file: `ParseException::$sqlLine`, else line 1. Issues and incomplete constructs are not diagnosed.
  - The installed `AnalyserResultFinalizer` skips `CollectedDataNode` rules when nothing was collected, so a standalone rule cannot serve as the hook.
- **Fetched types.**
  - One mapping, keyed by connection driver and column family and shared by the migration and dump paths, gives a read type (fetched) and a write type (accepted). Nullability applies next, then the fetch-option transformations. Explicit casts, the implicit incrementing-key cast (`HasAttributes::getCasts()`), dates and accessors take precedence.
  - Both paths produce schema-parser `ColumnType` facts, resolved at lookup so option changes need no reaggregation. A Blueprint type maps directly to the type its driver's grammar emits, limited to facts inference needs, with PostgreSQL's canonical `pg_catalog` identity. The grammar is not run: MySQL's `typeDate()`/`typeYear()` read the live server version. Blueprint CHECK-backed enum values (pgsql, SQLite) are analyzer column metadata, not `ColumnType::$values`. `rawColumn()` reads `mixed`.
  - Dates read `CarbonInterface` (`asDateTime()`), immutable casts `Carbon\CarbonImmutable`; date writes accept `DateTimeInterface|string|int|float` (`fromDateTime()`). The soft-delete column is a date only when it has no cast, an undetermined one included, as `initializeSoftDeletes()` adds its `datetime` cast only then.
  - `ModelHelper` runs the trait initializers (`initializeHasTimestamps()`, `initializeHasUniqueStringIds()`) before `initializeModelAttributes()` on the memoized constructor-less instance, and nothing mutates it later, so key type and incrementing never depend on call order (upstream set `usesUniqueIds` inside `ModelCastHelper`). Cover property-before-casts access.
  - Upstream differences, each commented at its mapping:
    - Uncast decimals read `numeric-string` on MySQL/MariaDB, `string` on pgsql (numeric holds NaN/Infinity) and `float|int` on SQLite. They are written as `float|int|numeric-string` (`float|int|string` on pgsql).
    - Booleans read `int` (`tinyint(1)`) except `bool` on pgsql.
    - pgsql `bytea` reads `resource`. Binary columns on every driver (`bytea`, MySQL/MariaDB binary and blob types, SQLite blob affinity) also accept a stream, which `PdoConnection::bindValues()` binds as a large object.
    - MySQL/MariaDB `BIGINT UNSIGNED` and `BIT(64)` read `int<0, max>|numeric-string`, because values above `PHP_INT_MAX` fetch as strings; shorter `BIT` columns read `int<0, max>` (native and emulated prepares fetch them as integers). There is no foreign-key or auto-increment shortcut; the implicit key cast types `$model->id`.
    - MySQL/MariaDB `SET` reads `string`: it holds comma-joined combinations, not one label (upstream used the labels' union).
    - SQLite numeric affinity reads `float|int` only for `numeric`/`decimal`; other names with numeric affinity (`uuid`, `string`, `geometry`) and untyped columns read `mixed`, because SQLite keeps non-numeric values as written.
    - SQLite `json`/`jsonb` columns read `float|int|string`: numeric affinity stores a JSON number as a number, which PDO fetches as one. Blueprint `json()`/`jsonb()` create them only under the connection's `use_native_json`/`use_native_jsonb`, else `text`; the two flags join the endpoint identity and the aggregation fingerprint.
  - Booted connection `options`, merged as in `Connector::getOptions()`, adjust the read types:
    - `ATTR_STRINGIFY_FETCHES`: int families, MySQL/MariaDB decimal and double, and integer-backed booleans become `numeric-string`. pgsql numeric and float and SQLite real become `string` (`'NaN'`, `'NAN'`, `'INF'`). pgsql bool becomes `'0'|'1'`.
    - `ATTR_ORACLE_NULLS`: `NULL_TO_STRING` replaces null with `''` (`TypeCombinator::remove()`, which also subtracts null from `mixed`); `NULL_EMPTY_STRING` adds null where `''` can be read.
    - The column's nullability applies to every converted type: a known NOT NULL column subtracts null (`TypeCombinator::remove()`), so an unknown type, an unmapped name or an unresolved PostgreSQL type starts as `mixed~null`, else `mixed`, and passes through the same options. Write types keep `mixed`, since PHPStan's `MixedType::accepts()` ignores a subtracted null. Read nullability is whatever the resulting type allows (`! isNull()->no()`), never a separate flag; write nullability stays the column's. The exception is a cast `castAttribute()` reads through `fromJson()` (`array`, `json`, `json:unicode`, `object`; `ModelCastHelper::readsEmptyStringAsNull()`), which also reads `''` as null: a nullable fetched column reads null through it whatever the fetch options, because `NULL_TO_STRING` fetches its null as `''`.
    - `ATTR_CASE`: folds fetched attribute names at the property lookup, not the schema names, cast lookups or write targets.
  - Drivers without a mapping read `mixed`.
  - SQLite types describe the framework's standard writes, not engine enforcement; STRICT tables do enforce their types. Explicit casts give stable application types.
- **Casts.** `ModelCastHelper` merges the runtime `$casts` property (with the implicit key cast) with `casts()`, read statically. It never runs `casts()`: one reading constructor-initialized state fails on the constructor-less instance.
  - The framework's default `casts()` is skipped. With `parseModelCastsMethod`, an override is parsed with `@cachedRichParser` (the cleaning parsers strip method bodies), found by its native file and start line (traits, several classes per file). Only a single unconditional top-level array return is read; returns inside nested function-likes are ignored. It is evaluated in the declaring class's scope, so an inherited `self::` resolves and a non-final `static::` stays unknown.
  - Cast names normalize as `getCastType()` reads them: a `date:`/`datetime:`/`immutable_date:`/`immutable_datetime:`/`decimal:` cast with arguments and a known class keep their spelling; anything else is trimmed and lowercased whole, so `ENCRYPTED:ARRAY` reads as `encrypted:array`. Runtime fix: `isClassCastable()` also tests `getCastType($key)` against the primitive list, so a primitive cast in another case (`BOOLEAN`) no longer throws `InvalidCastException` on write; regression in `DatabaseEloquentModelTest`.
  - Values: constant strings verbatim (PHPStan already unescapes PHPDoc strings), the `[$cast, ...$arguments]` list normalized as `ensureCastsAreStringValues()` does, anything else undetermined. The constructor-less instance skips `initializeHasAttributes()`, so its `$casts` property values get the same normalization. The source types declare that form: `$casts` and `casts()` accept `[$cast, ...$arguments]` lists (arguments may be ints), while `getCasts()` stays normalized `array<string, string>` (`types/Database/Eloquent/Casts/CastDeclarations.php`).
  - `AsCollection`/`AsEncryptedCollection` read the collection class `using()` selects, with its templates at their bounds, when no mapper is given; with a mapper, the base `Collection`. An undetermined parsed value falls back to the same required key of the declared return shape; an unusable parse uses the declared shape.
  - One shape not explicitly open (`...`) is complete: its required entries override the property casts and its optional entries are undetermined. `isUnsealed()` is `maybe` for ordinary shapes outside bleeding edge, so completeness tests `! yes()`. An open shape, several alternatives or a non-constant type leaves every attribute it does not require undetermined.
  - `ModelCastHelper::getCastClass()` reads a class cast as `isClassCastable()` does: the type before `:`, never one of the runtime's `$primitiveCastTypes` (class names are case-insensitive, so `datetime` would otherwise name `DateTime`). The computed-property check and serialization use it.
  - `hasCastForProperty()` includes undetermined casts; `getCastForProperty()` returns null for them. An undetermined cast reads and writes `mixed` (a date column keeps the date write type, since `fromDateTime()` runs first) and serializes as `mixed` even beside an accessor, because class casts serialize first. A key without a known column still applies its casts.
  - Cast types follow the runtime. A class caster's `get()` and `set()` also run for null, so a nullable column adds null to the read type except for a `CastsAttributes` caster (its declared `get()` return decides) and to the write type except for a class caster (its `set()` value parameter decides). A `Castable` uses the single caster class its `castUsing()` declares for the cast's arguments; an ambiguous one reads and writes `mixed`. `AsArrayObject`/`AsEncryptedArrayObject` read a benevolent `ArrayObject|null`, since their `get()` returns null for a missing or non-array value. Enum writes accept what `setEnumCastableAttribute()` accepts: the enum, plus `string` (case name) for a pure enum, `int|numeric-string` for an int-backed one and `string|int` for a string-backed one. An attribute whose column or nullability is unknown may hold null; a known NOT NULL column with an unknown or unmapped type reads `mixed~null` unless a fetch option can produce null. A class cast serializes with null added when the value may be null, since `addCastAttributesToArray()` serializes only a set value.
  - `CastDefinitionDynamicStaticMethodReturnTypeExtension` types an explicit map of framework helpers (`AsArrayObject::nullable`, `AsBinary::of`/`ulid`/`uuid`, `AsCollection::nullable`/`of`/`using`, `AsEncryptedCollection::of`/`using`, `AsEnumArrayObject::of`, `AsEnumCollection::of`) as the string the real helper returns. It applies only when the receiver is exactly the declaring class (a subclass could redirect `static::` calls) and every argument is a single constant its parameter type accepts; arrays only as callable mappings that `is_callable()` accepts. Otherwise the declared `string` applies.
  - PHPStan reanalyzes dependents only when declarations change. The model's metadata tracking (Result-cache correctness) covers the method's file; parsing also tracks, on the model, the files the constants and static methods its return uses come from (`SourceFiles`). The helper extension tracks its own source on the caller scope.
  - Regressions: `Type/data/model-casts-parsing.php` and the warm body-edit case in `ModelPropertyDependencyTest`.
- **Assignment.** `ModelProperty::canChangeTypeAfterAssignment()` is true only for raw schema attributes: no cast (including the implicit key cast and undetermined casts), not a date, and no accessor or mutator. PHPStan then narrows after assignment, while transforming attributes keep stable read types.
- **Accessors and mutators.** Each direction follows Eloquent's precedence, falling back to the database property (with its casts and dates) when it has no handler:
  - Reads: `get{Name}Attribute()`, then an `Attribute` get callback (`TGet` other than `never`). Writes: `set{Name}Attribute()`'s first parameter (`mixed` without one), then `TSet`.
  - A virtual attribute's fallback is raw `mixed` with its casts and dates; an uninstantiable model's is `mixed`.
  - Recognition matches `HasAttributes::hasAttributeMutator()`: a non-private method whose native return type names `Attribute` exactly. The generics come from PHPDoc; a bare `Attribute` is `<mixed, mixed>`, and PHPStan's `missingType.generics` reports the missing annotation. Public methods count; the visibility rule reports them separately.
  - Serialization prefers an `Attribute` getter to `get{Name}Attribute()` (after class casts), as `mutateAttributeForArray()` does, and converts dates only on the `Attribute` branch. A set-only `Attribute` serializes through the column's casts. Every appended attribute takes the `mutateAttributeForArray()` path too: a non-enum class cast (inbound or `Castable` included) reads as the attribute's readable type, so `get()`'s return or an inbound caster's raw value, without `serialize()`; else the getters; an appended attribute with neither is `mixed`, since `mutateAttribute()` then calls a missing method. An `Enumerable` converts element-wise only when its `toArray()` is `Collection`'s or `LazyCollection`'s; an override keeps its declared return.
  - Runtime fix in `HasAttributes::mutateAttributeForArray()` (Laravel shares both defects): enum casts skip the class-cast branch (`! isEnumCastable() && isClassCastable()`, as `isClassSerializable()` does), since instantiating the enum threw for an enum-cast column with a getter or in `$appends`; and the `Attribute` branch asks `hasAttributeGetMutator($key)`, since `cacheMutatedAttributes()` replaces the read cache with snake-case keys, making a camelCase appended accessor depend on whether a property read came first. Regressions for both.
  - Unlike upstream, a direction without a callback is not `never`, legacy setters type writes, and bare or public `Attribute` methods are not hidden.
  - Regressions: get-only and set-only accessors over a column, a virtual fallback with a cast, legacy setter input, legacy getter precedence beside an unrelated camelCase method, bare and public recognition, set-only serialization through a cast, an inherited legacy getter beside a child `Attribute` getter, and the `Attribute`-only date conversion.

Track connection/table identity where it changes the result, schema changes across migrations, nullability, defaults, enums/casts and supported custom driver boundaries. If a dynamic migration or unsupported custom-driver construct prevents a complete schema, preserve known declarations and avoid reporting an unproven missing column. Do not turn all unknown properties into `mixed` globally or suppress unrelated mistakes. Preserve upstream extension points instead of inventing a driver plugin platform.

## Result-cache correctness and analysis cost

- Retain PHPStan's `DependencyTracker`/`DeclarationDependencyTracker` use for configuration, migrations, schema dumps, views and translations. Track both changed files and directory membership so newly added/deleted files invalidate results. Keep declaration-based dependencies for reflection extensions and scope-based dependencies for return types/rules.
- Config sources come from one place, `ConfigSourceResolver::getKeySources()`: in each config directory the file of every key prefix (existing or not) and the key's own directory (`*.php`, recursive, so a nested file created later is noticed), then the framework file and overlapping package merge files. `ConfigParser` uses it with its config directories and carries directories through its cached dependency records, so a value read through another config file replays them. The schema facts read the booted repository, so `ModelPropertyHelper` declares the sources of every key `ConnectionConfigResolver` read (its own and the migrations' connection keys, also on a `MigrationCache` hit) against the booted directories, once the facts are loaded, on `Model` and on classes using `model-property`. Regression: a warm run after a config edit that moves a migration to another connection. Provenance of runtime-copied files, provider writes and inputs, `.env` and environment identity stay with the shared tracking below; the final warm-cache verification covers all of them, including schema connection config. A directory a glob `configDirectories`, `databaseMigrationsPath` or `squashedMigrationsPath` entry starts or stops matching has no tracked path, so `GlobalInputsResultCacheMetaExtension` hashes the three resolved lists (`Support\DirectoryResolver::resolve()`, which the config and schema readers share and which needs no boot; configured order kept, a missing literal directory kept so it is watched before it exists) and a change invalidates the whole cache. Regressions: warm runs that add and then remove a config directory, and that add a migration and a schema-dump directory.
- Schema sources besides migrations and dumps: constants naming tables, columns or connections, `foreignIdFor()` model metadata and a migration's parents and traits. `SchemaAggregator` records their files: column-level ones (column names, allowed values, `foreignIdFor()` models) on the table, so only models reading that table depend on them; identity-level ones (table names, a rename's target, migration parents and traits) on every model through `Model`. A guard (`hasTable()`, `hasColumn()` and the like) reads one table's facts to decide what happens to any table, so that table's sources become sources of every fact. `MigrationCache` stores their hashes, validates them on a hit and replays them. Regressions: warm edits of a constant a migration reads and of one a guard reads.
- Model metadata. PHPStan's exported declarations omit property defaults and method bodies, and a changed constant reanalyzes only the files naming its class. `ModelHelper::getInstance()` therefore tracks, once per model on the model class, the files declaring it and its parents below `Model` with their traits, and the files of constants their property defaults read. A constant read through a class depends on that class and its parents up to the declaring one, which can override it, and on the constants its value reads (`SourceFiles`). An overriding `getConnectionName()` can read any config value and is not interpreted, so that model also depends on every booted config source (`ConfigSourceResolver::getAllSources()`: the config directories, the framework config directory and package merge files), computed once. Regressions: warm edits of a parent's `$connection` default and of the config such an override reads.
- Forwarded builder methods. A caller depends only on the class it calls through and the classes its types name, so a call through a model or relation never depends on the model's custom builder or query class. `BuilderDependencies` declares, per builder instantiation (`getCacheKey()`, since the query class can come from active template types), class dependencies on a custom builder and query class and the file declaring a custom `$passthru` (a property default, so not a declaration). It records them on the owner every caller depends on: the model for model calls, the related model for relation calls (never the shared relation class), the builder for direct calls. Both forwarding extensions register before resolving the method, so restoring a removed method clears the stale error. Macro registrations stay with the shared tracking below. Regressions: warm builder (passthru alone, then a declaration) and query-class edits with recovery, each route calling through its own classes so one route's inputs cannot mask another's.
- **Shared runtime inputs.** Every boot-derived fact (container keys, facades, macros and mixins, managers, auth guards, console definitions, storage disks, the morph map, queue routes and forwards, worker-state bindings/routes/middleware/listeners/Bus maps, the booted config the schema and queue rules read, translation and view registrations) declares one aggregated value, `RuntimeInputsResultCacheValueExtension`, through `Support\RuntimeInputs` on the scope or the declaration tracker, before every early return (misses, unresolved drivers and collector decisions depend on boot too). A class-level declaration reaches every file depending on the class or a descendant, so it is made only where the boot decides the fact: a macro lookup declares it once per class, and only for a Macroable class, a builder or a facade (any other class has no macros whatever the boot registers). Native per-file tracking would record about 75 values per call site. The main process restores the cache before it boots: workers fork from it after the restore and boot themselves, and the main bootstrap runs only after they finish. So the value is computed from its key alone and memoized per process. Workers inherit the classes the restore loaded, so a warm worker's key can list more boot-loaded files than a cold run's; that superset is kept (the extra entries are unchanged files), and the runtime-input tests prove cold → warm → warm runs stable. The key holds:
  - **Files**, by content or `missing`: everything `get_included_files()` holds after boot, except PHPStan's own files (`phar://` paths, the analyzer, and PHPStan's `tmpDir`: its compiled container embeds the run's environment, including the restart's per-run `PHPRC`, whenever a config file's mtime changes) and files under the realpath of Composer's vendor directory, unless their `installed.json` entry is a mirrored path repository (`dist.type: path`; symlinked path packages already resolve outside vendor). Plus Composer's `installed.json`/`installed.php`, the root `composer.json`, `bootstrap/providers.php`, the Testbench YAML candidates in the directory the loaded configuration names (`getConfigurationPath()`) and the application-mode environment files below. These listed files keep their own paths, never resolved, so a symlink pointed elsewhere is noticed; a generated cache output is still recognized by either spelling, since an included one arrives resolved. A class file is never excluded, because a registration helper's body can change bindings. Consequence: in the components repo and path-repository consumers, editing any framework file the boot loads reanalyzes every boot-fact consumer.
  - **Config directories** the boot loads (`ConfigSourceResolver::getBootedConfigDirectories()`), by the names and contents of their config files, so an added file is noticed (not through symlinked directories, which the loader's Finder does not follow). Not while configuration is cached: the boot then reads only the cache file, which the files entry tracks.
  - **Environment names and patterns** (below).
  - **Presence-only paths:** the Testbench SQLite file (below).
  - Paths under PHPStan's working directory are written relative to it (the value extension's `createKey()`), others stay absolute; `getValue()` resolves them, so `keyToResultCache()`/`keyFromResultCache()` are identity. This keeps the key small: every `ValueDependencyCollector::record()` call copies the whole key into its id (`getId()` concatenates the extension class and key) and PHP hashes that id as an array key.
- Per-fact sources besides the shared value: matched console commands' `SourceFiles` (a `$signature` default is not a declaration); config directory membership through native directory dependencies on `ConfigSourceResolver::getAllSources()`. PHPStan records a called method's declaring class, so a found macro or facade method needs nothing more (a closure's file ran during boot). A class the boot selected whose declaration decides a fact native recording misses gets a class dependency through `RuntimeInputs::trackClass()`: a facade root or default disk that lacks the method, a manager's driver behind a `ProxiedMethodReflection` (declared on the manager), and a guard whose methods `AuthManager` forwards. Where a method body selects the fact, `RuntimeInputs::trackSources()` adds the selecting class's `SourceFiles` below its framework base (memoized per class and base, declared on every call) on top of its class dependency, which still covers inherited declarations and the base class: the booted manager or bound subclass whose `getDefaultDriver()` picks the driver, the facade whose accessor picks the root, and the filesystem manager. Regressions: a warm body-only edit of a manager's `getDefaultDriver()`, and an edit of the interface whose PHPDoc a bound manager subclass's driver creator inherits (only the class dependency covers it). Resolving a binding can load its class after boot, and a declared type is read without loading it, so the shared value does not cover them.
- Scopeless consumers declare on a class: class reflection extensions on the class they describe; the morph map on the class whose PHPDoc uses a morph map type (`EagerLoadMapTypeNodeResolverExtension`, through `NameScope::getClassName()`: the Model and MorphTo stubs and Eloquent `Collection`'s own `loadMorph()`/`loadMorphCount()` docblocks); schema facts on `Model`.
- **View names.** `ViewStringType` asks the booted finder whether a view exists, which depends on which view files exist, never on their contents. A separate views key, so adding a view reanalyzes only view consumers: one `listing` entry per finder directory (`getPaths()` plus every `FileViewFinder::getHints()` path; a finder that is not a `FileViewFinder` contributes its paths), each digesting the sorted relative names of every file under it (pattern `*`: one walk, and a non-view file there only reanalyzes view consumers), served by `RuntimeInputsResultCacheValueExtension`. The walk follows symlinked directories, as the finder does, except a link to a directory it is already inside. Runtime-copy provenance compares the names only. `RuntimeInputs::trackViews()` declares the views key and the shared key (the finder's paths, hints and extensions come from the boot). No recording inside `ViewStringType`, which has no scope. Recording sites:
  - Class members: `ViewStringTypeNodeResolverExtension` declares on `NameScope::getClassName()` for `view-string` and for an identifier naming a type alias (global, or local and imported through the `NameScope`) whose resolution contains a `ViewStringType`: the extension resolves such an identifier through the `@api` `TypeNodeResolver` (leaving the nested call to core with a per-name guard) and returns the result (`TypeAliasResolver` is not `@api`). PHPStan resolves an alias in the scope of the class or configuration defining it, so this is the only point that sees the class using it. Covers the stubs (including the `@phpstan-assert-if-true view-string` on the View factory's `exists()`) and user classes and traits.
  - Free functions: `ViewStringFunctionDependencyRule` (`FuncCall`) tracks when the named function's parameter, return or assertion types contain a `ViewStringType` (`ViewStringType::occursIn()` traverses callable types; memoized per function, tracked on every matching call). Covers `view()` and user helpers.
  - The declaring file's own checks (a literal returned under `@return view-string`, a property default, an inline `@var`, a callable invoked through an aliased parameter): `ViewStringFileDependencyRule` (`FileNode`) tracks when the file's text contains `view-string` or the name of a global alias whose definition resolves to one (`TypeStringResolver`, computed once). A class file's own member checks also depend on it through the class declaration when PHPStan notes the file's own class.
- **View and translation files.** The unused-view and missing-translation rules read view and translation files through symlinked directories, as the finder and translation loader do (`Support\RecursiveDirectoryIterator::followingLinks()`, the walk the listings share). PHPStan's directory dependency does not enter linked directories, so the rules declare their view and translation directories through `RuntimeInputs::trackLinkedDirectories()`: one value per call over names and contents, following links, separate from the shared key so a template edit reruns only these rules. These directories and the view listings are recorded by their own paths with trailing separators trimmed, never resolved, so a symlinked root pointed elsewhere is noticed. Regressions: a warm run with collected-data error reuse after editing a linked template without renaming it, and keys recorded through `RuntimeInputs` evaluated again after a root link is retargeted with its old target unchanged.
- **Environment.** `bootstrap.php` captures `$_SERVER`, `$_ENV` and `getenv()` before boot; restoration reads the live maps. A name's digest is the triple each default adapter reads (ServerConst/EnvConst: a scalar, booleans as `'true'`/`'false'`; Putenv: a string), with missing distinct from `''`. Only digests are persisted. Names come from the retained boot sources, every included script, vendor ones too (framework config files, helpers such as `app_id()`), and, from versioned vendor packages, the boot-loaded class files of each package that supplies a loaded provider (a provider can delegate registration to a helper in its own package) plus every loaded provider's parent and trait files. Other vendor classes are not scanned: the dotenv adapters `Env` always loads, Symfony's `Request` and `CliDumper` would force the whole-environment fallback, and the rest read run-time terminal and IDE detection (`COLUMNS`, `TERM`, `NO_COLOR`) that would reanalyze every boot consumer when switching between editor and CLI. Content hashing and name discovery are separate selections. Recognized reads are constant names read by `env`, `env_array`, `env_or_fail`, static `Env::get`/`getArray`/`getOrFail`/`has`, `getenv()`, constant `$_ENV`/`$_SERVER` offsets and `Env::getRepository()->get()` (a first-class callable of any of these, such as `env(...)`, is a dynamic name); plus the names the selected env file interpolates (dotenv's `Parser`, `Value::getVars()` read with `Resolver`'s `${NAME}` pattern; no evaluation). `self::`, `static::` and `parent::` calls inside an `Env` subclass are `Env` reads. Whether a class is an `Env` subclass or a modeled reader is loaded is decided against the classes declared when `captureBoot()` ran, never the live state: extensions autoload classes during analysis, which would give the main process and the workers different keys. Dynamic names inside those reader functions and `Env` are plumbing. Modeled dynamic sites map to patterns: `HandlesDatabaseConnections::usesDatabaseConnectionsEnvironmentVariables` to `MYSQL_*`, `MARIADB_*`, `POSTGRES_*`; `EnsuresDefaultConfiguration::bootstrap` to `APP_KEY`, `APP_DEBUG`, `DB_CONNECTION`; `Application::normalizeCachePath` to `APP_*_CACHE`; `ParallelTesting::option` to `HYPERVEL_PARALLEL_TESTING_*`; Testbench's `defined_environment_variables()` to none (it forwards the environment to subprocesses). Patterns stay in the key and `getValue()` matches them against the incoming maps, digesting matched names and values, so a newly set variable is noticed. Patterns skip `PHPRC`: PHPStan's restart points it at a new temporary ini file on every run, which would make the whole-environment fallback never reusable; a named read still tracks it. Any other dynamic name selects the whole environment. The scan runs once per process, on first use, with PHPStan's non-cleaning simple parser (the cleaning one drops function bodies; the rich one doubles the cost), and skips only files matching neither `$_SERVER`, a word ending in `env`, `env_array` or `env_or_fail`, nor the short name of an `Env` subclass loaded at boot (case-insensitive), which every recognized read contains. The app, package and components repo boots assert that they do not fall back to the whole environment. Hashing the whole environment instead would lose reuse across sessions and CI runs (session identifiers, SSH ports, CI run ids).
  - Application mode tracks the base `environmentPath()`/`environmentFile()` captured once `bootstrap/app.php` returns (so `loadEnvironmentFrom()` is honored), its `.{APP_ENV}` candidate for the incoming `APP_ENV`, and the file selected after boot. While configuration is cached, `LoadEnvironmentVariables` skips the file, so neither these files nor their interpolated names are tracked or parsed (a malformed unused file must not fail analysis); the tracked config cache decides, and removing it restores them. Package mode loads no environment file: `Testbench::create()` leaves `load_environment_variables` false, applies the YAML `env`, and marks the kernel bootstrap complete.
- **Package provenance.** Package-mode boot paths point into Testbench's per-process runtime copy, which disappears between runs. `Bootstrapper` records the skeleton source of the copy it owns (`runtimeSourcePath()`). `RuntimeInputs` maps a path in that copy to the skeleton path when both have identical content or are both missing (a directory when names and contents match, through its symlinked directories for view and translation directories; a view listing when names match), memoized per path. The shared key and the narrower trackers (`ConfigParser`, `ModelPropertyHelper`, `ViewFileHelper`, `NoMissingTranslationsRule`) use it; parsers still read the runtime paths. The application's cache files (`getCached*Path()`) with no identical skeleton counterpart and Testbench's process marker are boot outputs and are excluded. Any other unmapped runtime path (an added or overwritten fixture file, a borrowed runtime, a predefined `BASE_PATH`) keeps its runtime path and invalidates conservatively. No blanket prefix substitution.
- Boot-derived config mutation targets depend on external conditions: Testbench rewrites `database.default` only when the SQLite database file is missing. When the bound `Foundation\Bootstrap\LoadConfiguration` is Testbench's loader (the application itself is a plain foundation application), the shared key holds that file's presence, whatever `database.default` now says, mapped to the skeleton by relative path (the rewrite runs right after the copy), never its content. No new tracking in the config parser, no boot during cache restoration.
- PHPStan 2.3.5 hashes the files of known extensions but not the list of attribute-registered services, so adding an `#[AutowiredService]` extension left warm results stale (the components repo and path-repository consumers; versioned installs are covered by `changedPackagesProvideContainerClass()`). The owner-approved `AttributeServicesResultCacheMetaExtension` hashes the sorted `%attributeServicesClasses%` list, with a removal `@TODO` and `AttributeServicesResultCacheMetaExtensionTest` (handoff `_tmp/pr-ideas/phpstan-new-attribute-services-result-cache.md`). Keep it separate from the shared runtime-input tracking so it can be removed on its own.
- **Pre-boot meta.** PHPStan computes meta once, in the main process before any boot. One meta extension hashes the global inputs: `HypervelStubFilesExtension`'s stub-directory membership (PHPStan rechecks recorded stub hashes but not a changed list) and the boot-identity selectors, which choose which application, loaders and registrations exist: `APP_ENV`, `APP_BASE_PATH`, `COMPOSER_VENDOR_DIR`, `APP_*_CACHE`, `APP_RUNNING_IN_CONSOLE` and `TESTBENCH_*`, digested like the environment value with patterns matched freshly. 2.3.5 deprecates the interface in favor of value tracking, but it remains the only mechanism that invalidates every file, so it carries a reasoned `class.implementsDeprecatedInterface` ignore. It stays separate from the attribute-services workaround. Do not serialize the live container or boot during cache restoration.
- Warm-versus-cold subprocess fixtures, reusing one app and one package setup:
  - App: a provider macro edit changes a valid call into an error and back, with a `mixin()` class referenced only by the provider; a body-only edit of a registration helper the provider calls; a route-file and a provider binding edit for the worker-state rule; adding a stub file; an `APP_ENV` change; an undeclared process-only config variable set and unset; a `${NAME}` interpolation in `.env` whose process value changes; main/worker digest consistency in normal parallel analysis; no whole-environment fallback; a facade root gaining a method the facade lacked and a manager driver's method changing (class dependencies); a morph-map edit seen by a collection `loadMorph()` call; views: a free-function `view-string` parameter with the view added, deleted and restored, a class-member caller, a namespaced (hint) view, a global type alias `Closure(view-string): void` invoked through a parameter, and a template-body edit with unchanged names that reanalyzes none of them.
  - Package (Testbench): an unchanged second run reanalyzes nothing although Testbench creates a new runtime directory; a skeleton config edit; a YAML `env` edit; a `MYSQL_DATABASE` override unset, set, unset; SQLite presence in both directions; no whole-environment fallback.
  - The components repo: no whole-environment fallback.
  - Show reuse through PHPStan's ordinary result-cache output; identical warm and cold diagnostics alone cannot show it. No timing threshold, benchmark, `--debug` or routine cache clearing.
- Preserve the migration cache's locking, second read under lock and atomic replacement. Port upstream `MigrationCacheTest` and dependency tests, then add the changed-fingerprint regression: `getMTime()` has whole-second resolution, so ordinary edit-and-analyze loops can reuse a stale schema after two edits in one second. Keep mtime fixed explicitly in this regression instead of relying on test timing or sleeps. Use existing content fingerprints or a once-per-input `xxh128` digest and add a short WHY comment at the change so an upstream sync preserves it. Preserve upstream's timestamp-change invalidation alongside content changes so existing applicable tests remain meaningful. The fingerprint also covers the normalized config the aggregation reads (statement-connection facts, routing, `database.default`, `Builder::$defaultMorphKeyType`) and the installed `hypervel/schema-parser` version and reference. Connection-name keys that migrations read are known only after aggregating, so the entry stores each one's presence and value and is used, on both reads, only while they match. No new concurrency suite is needed for unchanged locking. Keep one parsed-schema cache, bounded in-process reflection caches and normal PHPStan temp storage; no extra persistent metadata service.
- Keep runtime source changes free of analysis-only request overhead. Parse lazily, reuse reflection/ASTs, and do not resolve every container service or model for every node. Use ordinary bounded correctness runs during development; get fresh owner confirmation that the machine is idle before any benchmark. Compare representative runtime paths only when needed to assess a concrete cost.
- Final efficiency pass, after the shared tracking. Agents re-run the analyzer constantly while building and maintaining the components repo, apps and third-party packages, so re-runs must be fast. Owner requirement:
  - Treat this as an optimization round, not just verification. Find and implement worthwhile, straightforward improvements to startup cost, repeated parsing/reflection, duplicate work and cache reuse. Preserve correct diagnostics and dependency invalidation; prefer targeted reanalysis and reuse of unchanged results. Require evidence of benefit proportionate to added complexity, and reject brittle workarounds or elaborate machinery for negligible gains.

### Transaction dispatch

Use statically known configuration from the ported parser, plus statically known dispatch/job overrides. Never use a machine's `.env` value as proof that a deployment is safe or unsafe. Hypervel defaults `after_commit` to true except for `sync` and `database`; a same-connection database enqueue participates in the transaction, but another connection does not. Report only when the queue connection, driver, after-commit and outbox settings are all established; anything unknown stays silent. Upstream assumes Laravel's `after_commit` default and reports dispatches inside `DB::afterCommit()` callbacks.

- **Walk.** `DB::transaction()`, `DB::connection(x)->transaction()` and `ConnectionInterface` receivers, with a closure or arrow-function literal. Walk its body syntactically without entering nested function-likes or classes: they run later, never or at an unknown time (`DB::afterCommit()` callbacks, registered callbacks); a nested transaction is checked from its own call.
- **Transaction owner.** The full requested connection name, as `ConnectionResolver::connection()` keys its owner and pool: a constant name, with null or `''` meaning `database.default`, enums normalized. Equal names are one owner. `mysql` and `mysql::write` are distinct for a known non-SQLite driver and unknown for SQLite (shared in-memory aliases coalesce) or an unknown driver. A `transaction` frame among the enclosing calls (`CallStack::enclosing()`) is an enclosing transaction with an unknown owner, whatever `afterCommit` frames follow it (they attach to their own connection only); a `usingConnection()` frame makes a default-dependent owner unknown. Either silences the database-queue comparison.
- **Dispatch forms.** `Job::dispatch()`, `dispatchIf()` and `dispatchUnless()` when the called method is Foundation `Dispatchable`'s (a literal condition that fails dispatches nothing; any other condition may dispatch); the global `dispatch()` helper (resolved function identity) with a `new` job or a closure/arrow-function literal (`CallQueuedClosure` facts; its body is not walked); `Bus::dispatch(new Job)`. The job class comes from names only: the walker has no call-site scope, so a variable job is silent. `dispatchSync` and `dispatch_sync` run inline. A non-`ShouldQueue` job or one with its own `queue()` method is silent.
- **Settings**, per setting with the outermost chain call winning: `afterCommit()`/`beforeCommit()`; `onConnection()`/`allOnConnection()`; `viaOutbox()`/`withoutOutbox()`/`onOutboxDatabase()`. `afterResponse(true)` runs synchronously (silent); `afterResponse(false)` dispatches normally. A non-constant argument is unknown.
  - After-commit follows `Queue::shouldDispatchAfterCommit()`: `ShouldQueueAfterCommit` unless `afterCommit` is false, else a non-null `afterCommit`, else the connection's `after_commit` or driver default. A deliberate `beforeCommit()` or `$afterCommit = false` default is silent.
  - Outbox is `viaOutbox ?? (ShouldQueueViaOutbox || connection outbox)`; an explicit false wins.
  - Connection follows `ReadsClassAttributes::getAttributeValue()`: a non-null property differing from its default, else `#[Connection]` (each class, then its direct traits, then its parent; a trait's attribute belongs to the using class) unless a public non-null property is declared below the attribute's class, else the property. `''` selects `queue.default` without routes. Read through PHPStan reflection (`getAttributes()`/`getArgumentTypes()`, defaults through `InitializerExprTypeResolver`), never `ClassMetadataCache` or runtime reflection, which load analyzed code.
  - Constructor: the actual constructor (own, inherited or trait), following `parent::__construct()`, parsed with `@cachedRichParser` and cached per class. Writing `$this->{connection,afterCommit,viaOutbox,outboxDatabase}`, a promoted parameter with one of those names, an option method call, or any other `$this`/`self`/`static` call makes the settings unknown, except `Bus\Queueable`'s own `onQueue`, `allOnQueue`, `onGroup`, `withDeduplicator`, `delay`, `withoutDelay` and `through` (native file check, so overrides stay unknown).
  - Booted routes and forwards have no provenance: a matching `queue.routes` route with a connection, or any forward when the connection is not explicit, is silent. Forwards are read once through the analysis-only `->call()` pattern.
- **Drivers.** Report a built-in async driver (`background`, `deferred`, `beanstalkd`, `sqs`, `redis`) or `database` on a different known owner, with effective after-commit false, no outbox and no deliberate `beforeCommit()`. Failover delegates to its children, custom driver names are unknown and `sync`/`null` are synchronous: all silent. A replaced built-in connector keeps built-in semantics (Horizon's `redis`).
- **Dependencies.** Property defaults, constructor bodies and constants read by attribute arguments are not exported declarations. Track `SourceFiles::forInstance()` (base class nullable) and the files of the constants the consumed `#[Connection]` arguments read, replaying cached lists for every consumer. Routes and forwards join the shared runtime-input tracking.

Required positive fixture: source config names a database queue connection different from the business transaction, with `after_commit: false`, no outbox and no explicit safe dispatch. Required negative fixtures: same-connection database, configured after-commit, explicit after-commit callback, outbox, sync, deliberate before-commit and environment-dependent connection selection. Verify queue transport/database connection names at their owning boundaries rather than equating their string identifiers. Warm-edit regressions: a job constructor gaining `$this->afterCommit()`, a parent's `$afterCommit` default, a constant read by `#[Connection]`, and an inherited `handle()` gaining a cancellation check (`BatchableJobChecksCancellationRule`).

### Verified regression examples

Keep these as focused tests, alongside all applicable upstream cases:

```php
value(...[static fn (): int => 42]);
with(...[21, static fn (int $number): int => $number * 2]);
with(callback: static fn (int $number): int => $number * 2, value: 21);
```

All three return `42`; upstream's raw positional-argument checks misdiagnose them. A limited query over three rows can return `1` from `limit(1)->get()->count()` and `3` from `limit(1)->count()`. ## Hypervel rules

### Cancellation

Implement the concrete `docs/todo.md` patterns with PHPStan types and AST/control-flow information:

- An exact `catch (CanceledException)` that rethrows or stores the cancellation, followed by a broader catch that reports, retries, falls back or records an outcome; callback/I/O/cleanup failures can wrap cancellation before the broad catch sees it.
- `instanceof CanceledException` on a throwable not already narrowed by that exact catch, and `getPrevious() instanceof CanceledException` used to classify cancellation.
- Failure accumulation such as `$failure ??= $exception` where the value is the operation's retained failure and later cancellation would lose precedence.

Recommend `Coroutine::causedByCancellation()` and `Coroutine::preferCancellation()` at those sites. Use small shared expression/try-block helpers only where more than one rule needs them. Do not construct a general exception-flow interpreter or guess through arbitrary callbacks.

```php
catch (Throwable $exception) {
    if (Coroutine::causedByCancellation($exception)) {
        throw $exception;
    }

    // Existing ordinary-error handling remains here.
}

$failure = Coroutine::preferCancellation($failure, $exception);
```

Rules (`Rules/Coroutine/`, sharing `CoroutineRuleHelper`; first-class callables are never calls):

- `ExactCancellationCatchRule`: a catch naming `CanceledException` that rethrows its variable or assigns it (`=`, `??=`) to keep it, followed in the same try by a `Throwable`/`Exception` catch that does not separate cancellation. A catch that ends the operation (`return`) is a terminal boundary and stays silent. Separation is a body of only `throw $var`, a first top-level `if (Coroutine::causedByCancellation($var))` whose branch ends in `throw`, or a body that is one `if` on that guard (either polarity). Silent when every call in the try block is a native wait from a method table checked against the declaring class: Channel/`ChannelInterface` `push`/`pop`/`close`, WaitGroup `add`/`done`/`wait`, `Waiter::wait()`, the coroutine classes' `join()`. A local receiver has its try-entry type when the block only calls methods on it, or the class of one `new` assigned in a top-level statement before every call; any other write leaves it unknown.
- `ExactCancellationCheckRule`: `instanceof CanceledException` on a subject that may be a `Throwable` and is not already known to be a `CanceledException`; a tip gives the null/`Throwable` guard for nullable or mixed subjects.
- `CancellationPrecedenceRule`: `$kept ??= $caught` in a catch body, except in the non-cancellation branches of a top-level guard on the caught variable or after a positive guard whose branch exits. Also silent when the kept variable appears nowhere in the try block nor elsewhere in the catch body and its try-entry type without null is only `CanceledException`.
- Both catch rules skip nested catches that bind the caught variable again: the inner try reports its own catch.
- `NoRawSleepCallsRule`, `NoCoroutinesInTransactionsRule`: see Worker lifetimes and coroutine context.

Native-only Swoole/Hypervel channel, WaitGroup, join and Waiter operations can retain exact checks when they are the only work in the relevant try block. Do not exempt an entire file or method that also invokes user callbacks or cleanup. Preserve foreign/child ownership boundaries and cleanup-error reporting. Use `tests/Coroutine/CoroutineTest.php` cases for direct/wrapped/nested cancellation, Google's separate service cause, foreign and independent-child failures, and failure priority. Typed domain catches, failure observers and arbitrary ownership propagation remain runtime-review concerns, not purported static proofs. Legitimate exact checks use a local identifier suppression with a reason.

Conversions in the components repo: an exact catch backed by a broad catch becomes one broad catch opening with a `causedByCancellation()` guard that keeps the exact catch's cancellation-only cleanup and rethrows the same exception; cleanup-failure precedence and `??=` collection use `Coroutine::preferCancellation()`; translators check `causedByCancellation()` (keeping null/`Throwable` guards) before mapping, and a catch that wraps failures in a domain exception rethrows a carried cancellation unchanged. Test-harness cleanup accumulators follow the same `preferCancellation()` policy; only `RunTestsInCoroutine::$capture` keeps the first failure, with a reasoned ignore, so PHPUnit can match the test's expected exception. Terminal reporters that deliberately report cleanup failures carrying cancellation and classification primitives keep exact checks with reasons. Packages gaining a `Hypervel\Coroutine` import declare `hypervel/coroutine` directly.

### Telemetry cancellation completion

The checkpoint immediately after the cancellation rules. Today a canceled operation never ends its span: `HttpServerInstrumentation` ends the request span only in `responseSent()`, which `Server` skips on cancellation, and the console, gRPC, scheduler, view, Scout and WebSocket observers return early or are never notified (`ScheduleRunCommand`, `View::renderContentsWithObservers()`). Child spans that ended earlier are still exported (`BatchSpanProcessor`) under a parent that never is, and the active-request counter's `add(-1)` (in `responseSent()`'s `finally`) is skipped, so it drifts upward. OpenTelemetry requires created spans to be ended; ending is separate from recording an error.

End spans, take state, close scopes, record durations and settle counters at the operation's real unwind boundary, through the existing observers, events and `finally` paths. No coroutine-defer fallback (it gives wrong durations and loses failure context), no fake `ResponseSent` or success event, no lifecycle registry, no dispatcher change to continue past throwing listeners. Disabled instrumentation keeps its behavior.

**Outcome policy.**

- A direct cancellation (exactly `CanceledException`) ends the span with status unset and no `error.type`, exception event or exception-context association, and still records duration and settles counters. Docs call this Hypervel's control-flow policy; the OpenTelemetry HTTP client rule is cited only for the HTTP client. A cleanup failure wrapping cancellation is a failure.
- Omit outcomes that never happened (HTTP status and response attributes, gRPC status, console and scheduler exit code, the custom `result` attribute). Keep outcomes already known (a sent response, an exit code, an earlier ordinary failure) and real domain statuses (gRPC `Cancelled`, `DeadlineExceeded`). No invented canceled status or exit code.
- Exact checks: one `AbstractInstrumentation::isDirectCancellation()` with one reasoned ignore ("only a direct cancellation is not a failure; a cleanup failure carrying it is recorded as one"); `OpenTelemetryManager::trace()` keeps its exact catch with that reason; Sentry has its own helper (below). These replace the temporary "skips completion" ignores.
- Completion applies the known outcome before optional enrichment callbacks, so a canceled callback can't drop it: `HttpServerInstrumentation::responseSent()` sets the status before user-context resolution; `RedisInstrumentation::recordCommand()` applies the exception and status before the query-text resolver, with duration and `end()` in `finally`. `CacheInstrumentation` counts the operation before key resolution (drop the old-policy comment). Database spans are retrospective; unchanged.

**Notification boundaries.**

- Observer APIs (View rendered observers, Scout `EngineOperationObserver`, gRPC `GrpcOperationObserver`) always finish already-started observers with the throwable, cancellation included. When one throws, notify the rest, then rethrow with `Coroutine::preferCancellation()` precedence. An observer that rethrows the operation's own throwable adds no failure: each loop skips it by identity, because its owner already propagates it. Docblocks say observers receive a "failure or cancellation".
- Existing end events are dispatched on cancellation, carrying it: console `AfterExecute` (already does), `JobAttempted` (below), WebSocket `MessageHandled`, and `ConnectionClosed` even when an earlier close step was canceled.
- WebSocket native callbacks (`onMessage()`, `onClose()`, `deferOnOpen()`) treat a wrapped cancellation like a direct one: it stops the remaining steps and deferred callbacks, completes through the cancellation helpers, and is reported as a real cleanup failure. `MessageHandled` keeps an earlier `MessageReceived` failure as its exception when the handler is then canceled. `reportCallbackFailure()` skips a direct cancellation, so every catch reports through it.
- `JobAttempted` gains a trailing `public bool $canceled = false` (not `interrupted`, which `JobInterrupted`'s signal notice already means), and `successful()` is false when it is set. Worker and SyncQueue dispatch it from the owning coroutine whenever `$canceled` is set, including the kill-mode branch where the body returned and the monitor owns the outcome; their other skipped steps (marker clear, timed-out event, invalid-payload report) stay skipped. `exception` is `timeoutExceededException($job)` when timed out, else the known failure, else the captured cancellation; `forJob()` is unchanged. A listener failure propagates when nothing is unwinding (the body-returned branch), otherwise `FailureReporter::report()` contains it. Foundation's deferred-callback listener and the slow-job handler (`whenJobRunsLongerThan()`) skip `canceled` attempts, keeping today's behavior; ActivityLog and Tenancy listeners keep their normal role and order. User listeners now see canceled attempts; `queues.md` documents it.
- Three new events, named after Laravel's `BatchCanceled` and dispatched only when they have listeners. Each carries `public Throwable $cancellation` (direct or wrapping) and `?Throwable $exception`, the operation's already-known failure. They are raised where an outcome notification was skipped or interrupted, from facts the emitter already holds; no listener-history reconstruction or tracking. Consumers classify: a known `exception` is a failure; otherwise a known outcome (a sent response, a finished task, a queued job) stands whatever the cancellation is, since it came from a notification listener; otherwise a direct `cancellation` is canceled and a wrapping one is the failure. Sentry's request transaction is the exception: a sent response's HTTP status stays its status (below).
  - `Hypervel\HttpServer\Events\RequestCanceled extends Event`: `exception` (the base contract) is `Server`'s earlier lifecycle failure (kernel escape, earlier send or listener failure); `response` is set only when its send attempt finished. Covers `RequestReceived` through `Kernel::terminate()` (handshake: `terminateRouteMiddleware`; Reverb has no terminate stage), because Sentry completes in terminate. Dispatched by the http-server `Server`, the WebSocket handshake and Reverb's `HttpServer`. OTel's `completed` flag ignores a notification after completion.
  - `Hypervel\Console\Events\ScheduledTaskCanceled(Event $task, Throwable $cancellation, ?float $runtime = null, ?Throwable $exception = null)`: `runEvent()` protects from the `ScheduledTaskStarting` dispatch (a later Starting listener can cancel after telemetry started) through the outcome notifications. `runtime` is set only when the task finished running, so a listener reads `exitCode()` only then (the public fallback can hold a stale run's value). `exception` is the task's failure when cancellation followed it. Telemetry keeps a finished task's outcome.
  - An ordinary failure before the task ran (a Starting listener, `registerRunningEvent()`) publishes `ScheduledTaskFailed` without a runtime, then rethrows the original so the run still aborts as upstream; a canceled Failed notification becomes `ScheduledTaskCanceled` with the failure as `exception`.
- A listener failure raised while a cancellation is being notified never replaces it: a direct cancellation is dropped, any other failure is reported through the boundary's never-throwing reporter (`Hypervel\Support\FailureReporter::report()`, WebSocket `reportCallbackFailure()`, Reverb's `FailureReporter`). Applies to `RequestCanceled`, `ScheduledTaskCanceled`, `JobQueueingCanceled` and canceled `JobAttempted`.
- `Hypervel\Support\FailureReporter` holds `PoolErrorReporter`'s unchanged body (skip a direct cancellation, drop a handler-raised cancellation, `error_log` fallback, never throw); `PoolErrorReporter::report()` forwards to it, and its tests moved to `tests/Support`. `FailureReporter::preferCancellation()` selects with `Coroutine::preferCancellation()` and reports the distinct displaced throwable. Reverb's `FailureReporter` keeps its own fallback (it logs the original and the reporting failure) and only gains the direct-cancellation exclusion.
- Displaced failures are reported (not dropped) only on these observer and lifecycle paths: View `renderContentsWithObservers()` and `Factory::notifyRendered()`; Scout's observer loop and final selection; gRPC `GrpcOperationHandle::finish()`, including an observer failure it does not throw; http-server `Server`, Reverb `HttpServer` and the WebSocket handshake for a held ordinary failure displaced by cancellation or by an earlier failure; the queue producer's `enqueueNow()` pair, `notifyBatchMembers()`'s retained ordinary failure when cancellation hides it (one per batch, as today), and the SQS tail's rejection when cancellation displaces it. The other `preferCancellation()` uses keep the documented first-failure convention.
  - `Hypervel\Queue\Events\JobQueueingCanceled`: `JobQueueingFailed`'s fields plus a required `bool $sendAttempted`, `bool $queued`, `cancellation` and `?exception` (the send failure when its `JobQueueingFailed` dispatch was interrupted). `queued` is true only when raised from the Queued helper: storage succeeded, so consumers keep the success outcome (Sentry `ok`, OTel no error) whatever the cancellation is, while the cancellation still propagates. It stays separate from `sendAttempted`, because a failed send was attempted but not queued. `raiseJobQueueingFailedEvent()` and `raiseJobQueuedEvent()` raise it from their known facts when their own dispatch is canceled, so `enqueueNow()`, the bulk paths and the outbox share one boundary.

**Queue producer.**

- `JobQueueingFailed` gains a trailing `public bool $sendAttempted = true`; the default matches today's counting, and framework call sites pass it explicitly. The flag is set at the actual storage or send call: `enqueueNow()` just before `$callback()`; Redis and Database bulk just before `pushRawBatch()` or the insert; SQS through `$attemptedMessageIds` per chunk, passed per message by `raiseBatchFailedEvents()`; `StagesOutboxJobs` at the outbox insert, per group.
- Cancellation catches notify outstanding members with `JobQueueingCanceled` before rethrowing. `notifyBatchMembers()` continues past a member's cancellation, notifies every member, rethrows the cancellation at the end (with `preferCancellation()`) and still returns the first ordinary failure. `enqueueNow()` still raises `JobQueued` when `handlePayloadPushed()` is canceled, then rethrows; the bulk paths get this through `notifyBatchMembers()`. Storage succeeded, so nothing is reported failed or stored again.
- `finishProducer()` always ends the span and records duration, but counts a sent message only when `sendAttempted` is true (a pre-send failure or cancellation is not an attempt). The counter description becomes "The number of messages the producer attempted to send." A failure or cancellation in the instrumentation's own finalizer completes its started state directly through the shared `completeProducer()` (not sent, no stored state), since no later event can find it.
- Correlation keeps `QueueProducerStateStore`'s payload buckets and UUID index; `createObjectPayload()`/`createStringPayload()` always set the UUID and finalizer rewrites keep it. Docs state the real boundary: a span stays open only for a payload lacking the framework UUID that a later finalizer rewrites. Don't describe custom drivers as unsupported.

**gRPC.**

- `Call::__destruct()` finishes an unfinished call with the state's known, nonblocking `finalStatus()`/`finalFailure()` through `resolveStatus()`, using an unknown result only for really abandoned work. `abandonIfIncomplete()` runs in `finally`, inside the destructor's existing no-throw catch. No waits or retries. Canceling one waiter must not end the shared call.
- `GrpcInstrumentation::startClient()` completes its own state when the propagation inject is canceled. `Server`, `GrpcOperationRunner`, `GrpcOperationHandle` and the `BaseClient` start path finish with the cancellation.
- `Server::onRequest()` finishes a canceled call with an earlier terminal failure as its outcome, but the unwinding cancellation keeps precedence there: an observer failure raised by that `finish()` is reported, and a direct one dropped.

**Sentry** (bounded audit of state-holding integrations). The request transaction finishes through a `RequestCanceled` listener resolving the scoped `Tracing\Middleware`. The scheduler and queue-producer integrations handle the new events. The consumer finishes the active, unfinished job span on a cancellation `JobAttempted`, preserving nested-job scope, reporting and already-finished spans. Direct cancellation leaves the status unset (sentry-php has no `cancelled` factory, and its constructor is private); wrapped and earlier failures keep the failure status, except on a request whose response was sent: its HTTP status stays the transaction status, as in `terminate()`, and the earlier failure is reported as its own event. Overriding it only when a later listener is canceled would make the same request report differently. One `WorksWithSpans::cancellationStatus()` holds the exact check. Cron check-ins: `ScheduledTaskFailed` and a failure-classified `ScheduledTaskCanceled` send `error` for the task coroutine's unfinished check-ins (a failed or canceled run can skip the after callbacks that finish them), listening whether or not spans are recorded. A direct cancellation sends none (`CheckInStatus` has only ok/error/inProgress); `src/docs/sentry.md` says Sentry then reports the run timed out because its final check-in never arrived.

**Docs and tests.**

- Rewrite `src/docs/opentelemetry.md`'s cancellation paragraph, its gRPC "no false completion" sentence, the queue paragraph on UUID-less rewritten payloads and the counter description. Document the new events beside their siblings.
- Convert the existing "no false completion" OTel tests into completion assertions. Regressions: a canceled request's span ends and the active-request counter returns to zero, including cancellation in `terminate()`; a Starting-listener cancellation; an interrupted Failed notification keeps the task or send failure, and an interrupted Queued notification keeps the publish success; a pre-send cancellation or failure is not counted as sent; post-storage cancellation still raises `JobQueued`; batch notification continues past a cancellation; Call destruction of abandoned streaming work, of an already-completed unconsumed result, and with a throwing observer still releasing native resources; a canceled Redis resolver keeps the command's outcome (successful and failed, direct and wrapped); a canceled consumer attempt ends its span and restores the scope (direct, wrapped, timeout, after a failure); an instrumentation finalizer failure records duration; a wrapped cancellation stops WebSocket message, close and open work; Sentry request, scheduler, producer and consumer completion; one per changed observer path, including an observer rethrowing the operation's throwable. Listener and observer assertions record events and assert after the call, because a failing assertion inside a reported listener would only reach a reporter.

### Worker lifetimes and coroutine context

Use actual container semantics: unbound buildable classes auto-singleton unless intrinsically fresh; explicit registrations, `Scoped`/`Singleton`, `Transient`, `SelfBuilding`, execution-scoped constructor attributes and contextual parameterized construction change the lifetime. Do not classify every mutable object as a singleton or every singleton mutation as unsafe.

Generic writes on shared objects are not reported: deliberate worker state (driver and store caches, lazily resolved config, registries, pools, worker loops) is the norm and no exemption marker exists. Detection covers only the cases below; legitimate exceptions take reasoned local ignores.

**Architecture.** One `Rules/Coroutine/WorkerStateRule` on `CollectedDataNode` reports all four identifiers.
- Registered unconditionally with the four switches injected (`Conditional` cannot express OR); it returns at once when all are off, and the collectors decline work too.
- Collectors hold only boot-independent facts, because PHPStan caches collected data per file: `WorkerStateWriteCollector` (`PropertyAssignNode`), `WorkerStateCallCollector` (`CallLike`: resolutions, route actions, direct `$this->method()` calls, config calls), `WorkerStateClassCollector` (`InClassNode`: `#[Singleton]`, `ShouldQueue`, promoted captures), `WorkerStateParameterCollector` (`VariableAssignNode`: reassigned state and config parameters) and `WorkerStateConfigOffsetCollector` (`Stmt`: config offset set and unset statements).
- Booted facts apply only in the rule and are read once. Never call `isShared()`/`isScoped()`/`class_exists()` or construct anything from analyzed code: class facts come from PHPStan reflection, attribute arguments from its constant evaluation.

**Roots** are walked for dependencies; only shared ones are receivers. They are registered bindings and instances, booted route controllers and route middleware, kernel and router middleware lists, class-string listeners, Bus-mapped handlers, collected parameterless constant resolutions, `#[Singleton]` classes and jobs. A job is a `ShouldQueue` class using the Bus `Dispatchable` trait (inherited uses count) that is not a mapped command; its `handle()`/`__invoke()` parameters are injection roots. Queued listeners and mapped commands are called directly. Handle-only dependencies of trait-less jobs are not discovered; the docs say so.

**Dependency paths** follow the entry point's real resolution:
- A `ContextualAttribute` comes first; its value is unknown.
- Constructors follow `Container::resolveClass()` with the built class as the contextual consumer: a default when unbound with no contextual binding of that exact name, a class-string contextual concrete followed as `make()`, a contextual closure unknown.
- Job handlers follow `BoundMethod` with the job as consumer: a default whenever the class is unbound.
- Controller actions and route closures follow `ResolvesRouteDependencies::transformDependency()`. A defaulted parameter is never resolved. A class parameter is skipped only when a route binding can supply it: any class when the route has an explicit binder, or a `UrlRoutable` named like a route parameter or its snake case (`ImplicitRouteBinding::getParameterName()`). A same-name scalar route parameter does not stop injection. Booted route closures are read for parameter names, types and attribute names only.

**Effective lifetime, explicit first.** An instance is shared; its constructor arguments are known only when its binding built the same class. A binding uses its class-string concrete as scoped, shared or fresh; an unknown factory is never executed and stops the walk; a fresh binding's inner concrete uses only an explicit lifetime. Unbound: `#[Singleton]` shared; `#[Scoped]` scoped; `SelfBuilding`/`Transient` fresh; an execution-scoped constructor attribute scoped (framework attributes decide by class, `Cache` by its constant `memo` argument, any other runtime decision is unknown); an interface, abstract or missing class, or `#[Bind]`/`#[BindWhen]`, unknown; otherwise an auto-singleton. The walk is memoized once per run.

**Contexts.**
- Booted middleware `handle()`/`terminate()` and controller actions, resolved on the class the container builds (a bound subclass included), keyed by the declaring method and recording whether any handling instance is shared.
- Helpers those methods and job methods call on their own instance. The call collector records direct, named `$this->method()` calls by caller (class and method), not inside nested functions and not first-class callables. `WorkerLifetimes` propagates each receiver's context with a worklist over receiver and declaring method (a visit as shared covers a later unshared one, not the reverse; edges indexed by caller and deduplicated). A call resolves to the caller class's own private method first, as PHP binds private calls to the calling scope, otherwise to the receiver's implementation; static methods and `__construct` are skipped, and `flushState()`/lifetime-tagged callers record no calls. Job roots are every queued class's job methods, shared only when the container shares that class. Propagated contexts go through the same `addContext()`, so write and config checks read one definition; config parameter provenance is unchanged. A helper reached only from a constructor or boot path gets no context. The write collector therefore keeps writes in any non-static, non-constructor instance method.
- Route closures and arrow functions passed as a route method's `action` argument (`Router`, `RouteRegistrar` or the `Route` facade). The call collector records the action's source range and the ranges of functions and classes nested in it; a collected position inside the action but outside those ranges runs in it. This is collected, so it also covers route files the analyzed boot does not load.
- `ShouldQueue` `handle()`/`__invoke()`/`failed()`, and `FormRequest` methods.

Functions nested in a context are not contexts. Ordinary listeners are not contexts, because boot events legitimately configure state.

**Known request/operation state**: a definite (null-removed) Symfony `Request` or PSR server request, Symfony or PSR response, `Authenticatable`, Symfony `UploadedFile` or Eloquent `Model`. Excluded: `Session` (`session.store` keeps its data in `CoroutineContext`) and `Route` (route registries hold routes).

**Skips.** Virtual properties (for example `TransformsRequest::$keyBytes`); `flushState()`; methods and constructors whose docblock has a line starting `Boot-only`, `Tests only` or `Boot or tests only`, single-line docblocks included (Passport writes "Boot-only when setting.").

1. `hypervel.workerSharedState`: a shared receiver keeps known state through a property write or a promoted or directly assigned constructor parameter, or writes a `$this` property inside a context whose handling instance is shared. An inherited booted method is judged by the instances that handle it, not by every shared subclass.
   - A constructor parameter is exempt only when the write comes before the constructor's first reassignment of it and, for every shared build of that constructor, the walk proves the default or a fresh instance of a known class, with no contextual attribute and no contextual binding for the actual consumer. Shared, scoped or instance bindings, closures, unknown factories, `SelfBuilding` and instances without a binding are not exempt.
2. `hypervel.staticStateMutation`, `hypervel.runtimeConfigMutation` and `hypervel.unboundedWorkerCache`.
   - `staticStateMutation`: a static property write inside a context, or a static property storing known state anywhere outside the skips.
   - `runtimeConfigMutation`: a config write inside a context: `config([...])`, repository `set`/`push`/`prepend`/`offsetSet`/`offsetUnset`, and statement-level offset assignments (compound included) and `unset`. The receiver is `config()`, the Config facade, a resolution without parameters, or with provably empty ones, whose name the booted alias map resolves to `config` (arguments bound by their real names: `abstract`, `resolve()`'s `name`, `get()`'s `id`; any unpacked argument declines) (no fixed name list; collectors keep the requested names), or a parameter the container injects into a controller action, route closure or job `handle()`/`__invoke()`: typed as a class the alias map resolves to `config`, without a default or contextual attribute; for a job, a contextual binding's replacement must also resolve to `config` (`Container::call()` makes the job the contextual consumer; route actions have none). Only writes before the parameter's first reassignment count; parameter facts keep the earliest reassignment position per function key (`class::method`, or `file#start` for a route closure, since closures in different files can share an offset). Locals and properties are not the global repository. The contract is not `ArrayAccess`, so PHPStan records offset writes on a contract-typed variable as variable writes, which count as reassignment.
   - `unboundedWorkerCache`: an offset set on static or receiver array storage that is not a constant array at the write (storage the method just reset holds only its own entries). The key must directly read `Request`/`Authenticatable`, `request()`/`auth()` or the `Request`/`Auth` facades, and its type must not be finite or an integer range bounded at both ends; bounds are checked before `getFiniteTypes()`. No taint tracking; `WeakMap`, `ArrayAccess` and unknown cache objects stay silent. The message says the storage can grow; intentionally bounded storage takes a reasoned ignore.
   - **Arbitration.** One diagnostic per write, among the enabled identifiers: `unboundedWorkerCache`, then `workerSharedState`/`staticStateMutation`.
   - **Cache correctness.** Under bleeding edge's `reuseCollectedDataRuleErrors`, the rule calls `trackClassDependency()` for every class whose lifetime or injection metadata it reads. `WorkerStateDependencyTest` edits a dependency's constructor and a lifetime attribute with the candidate file unchanged, with and without error reuse. Booted bindings, contextual bindings, routes, middleware, listeners and Bus maps use the shared runtime-input tracking.
   - **Runtime fix.** `Route::shouldCacheControllerOnRoute()` checks `isScoped()` (false), then `isShared()` (true), then any other bound class (false), and otherwise caches unless the class is `Transient` or `SelfBuilding`. Fresh controllers keep the coroutine-local path, so middleware and dispatch still share one instance. `RouteControllerCachingTest` covers both classes and explicit-singleton precedence.
3. Detect supported child-coroutine spawning APIs inside transaction callbacks when work is being moved off the transaction-owning coroutine. Explain that pooled database ownership belongs to the parent and the child does not inherit its transaction. Preserve established transaction-preserving test infrastructure and calls that do not actually spawn children. `NoCoroutinesInTransactionsRule` covers `go`/`co`/`parallel`/`wait`, the coroutine classes' `create`/`createOwned`/`fork`/`forkOwned`, `Parallel::wait()`, `Concurrent`/`WaitConcurrent` `create`/`fork`, `Waiter::wait()` and `CoroutineDriver::run()`, plus `run()` on the Concurrency facade or on `ConcurrencyManager` (its `@method run` makes the manager, not the mixed-in `Driver` contract, the declaring class) only when static config selects a default instance whose driver is definitely `'coroutine'` (an absent instance entry means its name; a present one needs its `driver` key), and the booted manager is exactly `ConcurrencyManager` with no custom creator for it. `driver()` on the facade and manager returns the known driver class by the same resolution (`ConcurrencyDriverHelper`, for a constant or enum name, with null or `''` meaning the default), else the `Driver` contract, so `driver('coroutine')->run()` reports. Only a sync driver runs tasks in place; tasks of any other `Driver::run()`, and of a facade or manager `run()` not known to use the sync driver, may run elsewhere and are a callback boundary. The innermost relevant enclosing call (`CallStack::enclosing()`) decides: `transaction` reports, `afterCommit`, a spawn frame or such a `run()` is a callback boundary. Evaluated, non-closure arguments of an in-transaction boundary call are searched for spawns, reported on their own lines. A known-empty task list (found by name or first position) is silent.
4. Diagnose raw source `sleep()`/`usleep()` where the documented replacement is `Hypervel\Support\Sleep`. Preserve real-time test/infrastructure waits and other explicitly justified timing contracts. The components repo keeps the `Sleep` and `Coroutine::sleep()` implementations, `LazyCollection`'s fallback without Support, prompts' animation timing, `StripedLock`'s spin backoff, `CurlStreamingBody`'s libcurl polling and Horizon's process supervision with reasons; `BenchmarkCommand`'s pause uses `Sleep`.

5. `RedisConnectionBoundMethodRule` reports a call that reaches `RedisProxy`'s stock `__call()` with a name in its `CONNECTION_BOUND_METHODS` (read once in the proxy's scope, not copied), which always throws there: `Redis::connection()->client()` and the like, on `RedisProxy` or `RedisManager` receivers. The `@mixin RedisConnection` chain otherwise accepts them; the facade already rejects them. It skips a native method accessible in scope (the proxy's own protected `getConnection()` calls, a public subclass method) and declines a receiver that overrides `__call()`, or for `RedisManager` `connection()`. The message names the held-connection replacement (`Redis::withConnection()`/`withPinnedConnection()`).

Use collectors only for cross-file binding facts needed by diagnostics. Derive known runtime registrations through existing bootstrap/reflection facilities when available. Unknown ownership must not produce a confident leak claim. Fix genuine violations and cover intentional patterns as negative fixtures. Do not add a separate policy framework, service registry, deep interprocedural data-flow engine or runtime instrumentation.

List-versus-map follows the literal's type; an uncertain shape or unpacked item stays silent.

  - Fix: only a `String_` is replaced, by an array of its exact segments (runtime-equivalent; Data flattens nested arrays, and `#[Rule([...])]` is its documented form). No fix when a segment is a regex rule, empty or untrimmed. The message names the replacement when fixable; otherwise a tip says a regex containing `|` must be its own array element.
